| 쪽지       | 발신자 정보를 받지 않는 익명 단방향 문의로 제공한다.                                     | 현재 API가 content만 수집하며 답장 계약이 없다.                              |
| 당근 링크  | 별도 필드를 만들지 않고 설명의 안전한 URL만 링크로 렌더링한다.                           | API 계약에 전용 링크 필드가 없다.                                            |
| 수정       | 텍스트 필드와 운반 도움 여부만 PATCH한다. 기존 사진은 읽기 전용이다.                     | 사진 추가·삭제·정렬 API가 범위 밖이다.                                       |
| 삭제       | 일반 확인 대화상자 뒤 바로 DELETE한다.                                                   | 세션이 소유권을 판별하므로 별도 비밀번호 확인 API를 만들지 않는다.           |

## 디자인에서 제거·변경하는 요소

- 층·엘리베이터, 가구 한마디, 이상형과 태그는 API에 대응 필드가 없어 제거한다. (가격은 Issue #150에서 다시 도입 — 아래 별도 절 참고)
- 찜 화면, 하트 버튼, 찜 수와 찜 배지는 관련 API가 없어 제거한다.
- 별도 당근 이동 버튼은 만들지 않는다. 설명 안의 안전한 URL이 있을 때만 링크로 연다.
- 쪽지 전송 성공은 판매자 쪽지함 API에만 반영되며, 발신자에게 보낼 편지함을 제공하지 않는다.
- 디자인의 비밀번호 본인 확인 화면은 수정·삭제 전용 화면이 아니라 보호 기능 진입용 로그인 오버레이로 재사용한다.

## 백엔드 의존성과 계약 충돌

- 백엔드 Issue #140이 실제 API 구현과 세션 인증을 제공해야 브라우저 통합 검증이 가능하다.
- 전달된 11개 API 초안에는 `POST /api/auth/signup`과 비밀번호 8~100자 규칙이 있으나, Issue #142 프론트 결정은 로그인 API 하나와 숫자 4자리 규칙이다. 서버는 `/api/auth/login`에서 미등록 번호 생성을 지원하고 4자리 규칙에 맞춰야 한다.
- 프론트와 API origin이 다르면 `credentials: "include"`가 동작하도록 서버의 credential 허용 CORS와 쿠키 속성을 배포 환경에 맞춰야 한다.
- 로그인 성공은 기존 회원 `200`과 신규 생성 `201` 모두 같은 `AuthMemberResponse`를 반환하는 것으로 사용한다.
- 받은 쪽지가 없는 매물의 `latestMessageAt` 표현은 초안에 정해지지 않았다. 프론트는 해당 경우의 `null`과 필드 생략을 모두 허용하며, 값이 있을 때만 최신 시각으로 사용한다.

## 후속 기능

- 찜, 읽음 상태, 익명 닉네임, 답장
- 별도 당근 URL 필드 (가격은 Issue #150에서 도입 완료)
- 서버 통합 쪽지함, 페이지네이션과 지역 필터
- 사진 추가·삭제·순서 변경, 판매 완료 상태
- 회원 탈퇴, 비밀번호 재설정과 휴대폰 SMS 인증

후속 기능은 별도 제품 결정과 API 계약 없이 이번 이슈에 추가하지 않는다.

## Issue #150에서 확정한 결정 — 매물 가격

| 주제 | 결정 | 이유·영향 |
| --- | --- | --- |
| 가격 필드 | 매물 관련 요청·응답 DTO에 `Integer` 타입 `price`(원)를 추가한다. 백엔드와 합의됨. | Issue #142에서 API 미대응으로 제거했던 가격을 서버 계약과 함께 되살린다. |
| 표시 범위 | 카드 조회(`ListingSummary`), 상세(`ListingDetailResponse`), 내 매물(`SellerListingSummary`)에 표시한다. | 구매자·판매자 모두 가격을 확인해야 한다. |
| 입력 범위 | 등록(`POST`)과 수정(`PATCH`)의 `ListingDraft`에 필수 필드로 넣는다. | 매물 생성·수정 시 가격을 함께 받는다. |
| 없는 값 처리 | 응답의 `price`가 `null`이거나 필드가 없으면 값을 지어내지 않고 **"표시불가"**로 렌더한다. | 서버 배포·데이터 마이그레이션 전 과도기에도 화면이 깨지지 않는다. `model/listingPrice.ts`의 `formatListingPrice`가 단일 처리 지점이다. |
| 입력 검증 | 0 이상 정수만 허용하고 상한은 1억 원이다(`MAX_LISTING_PRICE`). 숫자만 입력받는다. | 프로토타입 범위의 최소 방어. 0원(나눔) 별도 UX는 후속으로 둔다. |

### 백엔드와 확인이 남은 항목

- `ddl-auto: update`로 컬럼을 추가하면 **기존 행의 `price`가 NULL**이 된다. nullable 유지 여부와 기존 데이터 백필 정책은 서버에서 정한다. 프론트는 NULL을 "표시불가"로 안전하게 처리한다.
- 응답 세 DTO 모두에 `price`를 포함할지 최종 확인 필요(프론트는 세 곳 모두 소비하도록 구현했다).
