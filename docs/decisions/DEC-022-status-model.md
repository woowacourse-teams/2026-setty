# DEC-022 상태와 변경 주체

- 상태: **합의**
- 결정일: 2026-08-05
- 참여자: 캐리, 스마일, 밀란, 타스, 코코

## 결정

내부 운영 상태와 사용자 표시 문구를 분리한다. 예상 견적 요청의 첫 상태는 `검토 대기`, 배차 요청의 첫 상태는 `판매자 입력 대기`다.

- 예상 견적: `검토 대기`, `추가 정보 대기`, `견적 안내 완료`, `운송 불가`, `사용자 취소`
- 배차 요청: `판매자 입력 대기`, `최종 검토 대기`, `최종 금액 확인 대기`, `배차 대기`, `배차 완료`, `운송 중`, `배송 완료`, `최종 금액 거절`, `운송 불가`, `사용자 취소`, `배차 실패`

시스템은 제출·입력 완료 같은 사실에 따른 상태만 변경한다. 운송 판단·가격 안내·배차·예외는 운영자, 최종 금액 동의·거절은 구매자가 수행한다. 예상 견적 완료 후 별도 배차 요청을 만들며 견적 상태를 배차 요청 상태로 바꾸지 않는다.

## Issue #12 첫 검증 범위 적용

Issue #12에서는 `PENDING_REVIEW → ESTIMATE_NOTIFIED`만 구현한다. 운영자가 실제 문자를 보낸 뒤 문자 내용·운송 가능 여부·예상 금액을 한 번에 저장하면 `transportFeasible` 값과 관계없이 문자 안내 완료로 변경한다. `운송 불가` 상태를 삭제한 결정은 아니며 정보 부족·운송 불가·취소 전이는 후속 Issue에서 다시 검토한다.

## 검토한 선택지

- 내부·사용자 공통 최소 상태
- 모든 세부 단계를 한 상태 집합으로 사용
- 내부 상태와 사용자 표시를 분리

## 이유·영향

운영자는 수동 업무를 추적하고 사용자는 필요한 진행 정보만 보게 한다. 세부 사유·운영 메모의 노출을 막는 매핑 테스트가 필요하다.

- 검증 담당: 스마일, 기술 검토 밀란
- 개발 차단: 두 흐름의 저장·상태 API 계약 전에 승인본 확인
- 사용자 공개 차단: 역할별 상태·문구 검증 전 상태 화면 공개 불가
- 재검토: 새 운영 단계가 실제 반복될 때
