# SETTY 첫 개발 역할과 책임

- 상태: **첫 개발 역할 배정 반영·Issue 생성 전**
- 적용 기간: 첫 두 사용자 흐름이 개발 환경에서 연결될 때까지
- 원칙: 역할명보다 각 사람이 끝낼 사용자 결과와 GitHub Issue를 기준으로 나눈다.

## 1. 두 개발 흐름

| 흐름 | 인원 | 완료 결과 |
|---|---:|---|
| 예상 견적 요청 | 2명 | 사용자가 요청을 제출하고, 서버에 저장되며, 운영자가 신규 요청을 확인한다. |
| 배차 요청 | 3명 | 구매자가 실제 거래 정보를 입력하고, 판매자 입력을 받은 뒤, 운영자가 양쪽 정보를 확인한다. |

두 흐름은 별도 요청이다. 예상 견적 안내 문자에서 `배차 요청하기`로 들어와도 실제 거래 정보를 다시 입력한다.

## 2. 역할 5개

| 그룹 | 역할 | 맡는 결과 | 협업 상대 | 기본 검토자 | 완료 증거 | 실제 이름 |
|---|---|---|---|---|---|---|
| 예상 견적 | 견적 FE | 예상 견적 사용자 화면과 최소 운영자 확인 화면 | 견적 BE | 배차 FE | 정상·입력 오류·서버 실패 화면과 통합 확인 | 캐리 |
| 예상 견적 | 견적 BE | 견적 생성·검증·저장과 운영자 조회 API | 견적 FE | 배차 BE1 | API·DB 테스트와 견적 FE 연동 결과 | 밀란 |
| 배차 요청 | 배차 FE | 구매자 요청·판매자 입력·최소 운영자 확인 화면 | 배차 BE1·BE2 | 견적 FE | 구매자→판매자→운영자 전체 화면 증거 | 스마일 |
| 배차 요청 | 배차 BE1 | 구매자 배차 요청 생성과 판매자 입력 링크·세션 | 배차 FE·BE2 | 견적 BE | 구매자 요청·링크 발급·접근 테스트 | 타스 |
| 배차 요청 | 배차 BE2 | 판매자 입력 저장, 양쪽 정보 결합, 운영자 조회 | 배차 FE·BE1 | 배차 BE1 | 판매자 입력·권한·운영 조회 테스트 | 코코 |

배차 BE1과 BE2는 작업 전에 공통 데이터 경계와 API 계약을 함께 승인한다. 한 사람이 다른 사람의 저장 구조를 뒤늦게 맞추는 방식으로 진행하지 않는다.

## 3. 개발 시작 전 공동 작업

역할로 나뉘기 전에 다섯 명이 다음 순서로 공통 환경을 확인한다.

1. 초기 레포 설정 담당자 1명과 검토자 1명을 지정한다.
2. 담당자가 모노레포, 프론트·백엔드 골격, MySQL·JPA 개발 스키마 자동 생성과 개발 환경 변수 예시를 준비한다.
3. 다섯 명 모두 실제 레포를 새로 clone한다.
4. 모두가 프론트·백엔드 설치·실행·테스트·빌드를 재현한다.
5. 공통 설정 Issue를 닫은 뒤 각자 기능 Issue를 시작한다.

초기 레포 설정 담당: 밀란
초기 설정 검토자: 스마일

이 작업은 별도 장기 역할이 아니다. 먼저 끝내는 공통 작업 하나다.

## 4. 각자의 첫 GitHub Issue

| 담당 역할 | 첫 Issue |
|---|---|
| 견적 FE | `예상 견적 요청과 운영자 확인 화면을 만든다` |
| 견적 BE | `예상 견적 요청을 저장하고 운영자에게 제공한다` |
| 배차 FE | `구매자·판매자·운영자 배차 요청 화면을 연결한다` |
| 배차 BE1 | `구매자 배차 요청과 판매자 입력 링크를 만든다` |
| 배차 BE2 | `판매자 입력을 저장하고 운영자에게 양쪽 정보를 제공한다` |

각자가 자신의 Issue를 만들고 같은 흐름의 동료와 검토자가 포함·제외·완료 조건을 먼저 확인한다.

## 5. 검토 관계

- 견적 FE와 배차 FE가 서로 화면·사용자 흐름을 검토한다.
- 견적 BE는 배차 BE1의 API·저장 변경을 검토한다.
- 배차 BE1은 배차 BE2의 공통 데이터·링크·권한 변경을 검토한다.
- 배차 BE2와 견적 BE는 공통 DB·운영자 조회 충돌을 함께 확인한다.
- 작성자는 자기 PR의 최종 승인자가 될 수 없다.

작업량이 다르면 같은 흐름 안에서 하위 Issue를 새로 나누며, 다른 사람의 Issue에 범위가 기록되지 않은 코드를 조용히 추가하지 않는다.

## 6. 완료 판정

개별 FE·BE PR이 병합됐다는 이유만으로 흐름이 끝난 것은 아니다.

### 예상 견적 완료

- [ ] 사용자 제출이 저장된다.
- [ ] 운영자가 신규 요청을 확인한다.
- [ ] 입력 오류·서버/DB 실패가 성공으로 보이지 않는다.
- [ ] 가격 계산·문자 발송은 운영자가 수동 수행한다.

### 배차 요청 완료

- [ ] 구매자가 새 배차 요청을 만든다.
- [ ] 판매자 전용 링크가 발급된다.
- [ ] 판매자가 픽업 정보를 입력한다.
- [ ] 운영자가 양쪽 정보를 확인한다.
- [ ] 구매자·판매자가 서로의 상세주소·연락처를 보지 않는다.
- [ ] 실제 자동 배차·자동 문자는 구현하지 않는다.

## 7. 최종 확인

- [ ] 다섯 역할에 실제 이름이 한 명씩 있다.
- [ ] 초기 레포 설정 담당자와 검토자가 다르다.
- [ ] 각자의 Issue와 PR 검토자가 정해졌다.
- [ ] 견적 그룹 2명과 배차 그룹 3명이 각각 같은 완료 결과를 설명할 수 있다.
- [ ] 실제 개인정보 공개 전 DEC-020·021의 차단 조건을 확인했다.
