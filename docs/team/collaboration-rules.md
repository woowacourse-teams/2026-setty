# SETTY 협업 규칙

- 상태: **첫 개발 적용 초안**
- 기준: 복잡한 Sprint 관리 없이 GitHub Issue와 PR로 실행한다.

## 1. 가장 먼저 지킬 규칙

- 각자가 자신이 구현할 GitHub Issue를 만든다.
- 같은 사용자 흐름의 동료와 검토자가 Issue 범위를 먼저 읽는다.
- Issue 합의 후 `develop`에서 작업 브랜치를 만든다.
- 작성자가 아닌 팀원 1명이 PR을 검토한다.
- FE·BE PR이 각각 끝나도 사용자 흐름이 연결되지 않으면 완료가 아니다.
- 한 사람은 동시에 큰 Issue 하나만 진행한다.

## 2. Issue 최소 내용

```text
제목:
완성할 결과:
포함:
제외:
완료 조건:
연결할 화면·API·DB:
담당자:
검토자:
먼저 필요한 작업:
확인 방법과 증거:
```

별도의 “작업 카드” 문서는 만들지 않는다. GitHub Issue가 작업 설명과 진행 상태의 원본이다.

## 3. 두 흐름의 협업

### 예상 견적 2명

- 견적 FE와 견적 BE가 입력·요청·응답·오류 계약을 함께 정한다.
- 사용자 제출부터 운영자 신규 요청 확인까지 같이 검증한다.

### 배차 요청 3명

- 배차 FE·BE1·BE2가 구매자·판매자·운영자 화면별 계약을 함께 정한다.
- BE1과 BE2는 공통 모델·판매자 링크·상태·트랜잭션을 코드 전에 합의한다.
- 구매자 요청부터 판매자 입력과 운영자 확인까지 같이 검증한다.

## 4. Git과 PR

- `main`·`develop`에 직접 푸시하지 않는다.
- 작업 브랜치는 `develop`에서 만든다.
- 이름: `feature/<issue>-<slug>`, `fix/<issue>-<slug>`, `refactor/<issue>-<slug>`
- 기능·일반 수정 PR은 `develop`으로 보낸다.
- 작성자가 아닌 팀원 1명의 승인 후 Merge commit으로 병합한다.
- PR에는 결과·제외·테스트·수동 확인·문서 영향을 적는다.
- 백엔드 DEV EC2는 `main` 병합 시 자동 배포된다(DEC-026). 프론트 배포는 수동이다.

## 5. 완료 기준

- Issue 완료 조건을 충족했다.
- 관련 테스트와 빌드가 통과했다.
- 정상·입력 오류·서버/DB 실패·권한 시나리오를 확인했다.
- 같은 흐름 FE·BE가 개발 환경에서 처음부터 끝까지 재현했다.
- 문서와 실제 API·상태가 일치한다.
- 개인정보·비밀정보가 코드·로그·테스트·화면에 없다.
- AI가 만든 내용을 담당자가 설명할 수 있고 검토자가 확인했다.

## 6. 미정 정책 처리

- 기술 담당자가 입력·노출·상태·보관·운송 정책을 임의로 정하지 않는다.
- 필요한 결정과 막히는 작업을 Issue에 적고 `needs:decision` 또는 `status:blocked`를 사용한다.
- 개인정보·운송사 검증 미완료는 가상 데이터 개발과 실제 사용자 공개 중 어디를 막는지 구분한다.

## 7. AI 사용

```text
작업 Issue:
완성할 결과:
포함·제외:
완료 조건:
관련 문서와 DEC:
현재 브랜치:

먼저 적용되는 AGENTS.md와 범위를 요약해줘.
미정 정책이나 필요한 권한이 있으면 구현하지 말고 알려줘.
```

- 실제 이름·연락처·주소·사진·토큰·비밀을 AI에 제공하지 않는다.
- 같은 브랜치나 파일을 여러 AI가 동시에 크게 수정하지 않게 한다.
- 새 의존성, 삭제, 배포, 외부 메시지는 담당자 확인 없이 실행하지 않는다.

## 8. 팀이 추가로 정할 것

- 실제 이름과 검토자
- 초기 레포 설정 담당·검토자
- Vercel·DEV EC2 접근 담당·백업
- PR 확인 시간
- 사용자 문의와 긴급 연락 채널
