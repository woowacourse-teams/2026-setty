# 첫 개발 작업 계획

- 상태: **Issue 작성 전 초안**
- 목표: 복잡한 Sprint 운영 없이 두 사용자 흐름을 다섯 명이 나눠 구현하고 서로 PR을 검토한다.

## 1. 진행 순서

```text
공통 레포·실행 환경 준비
→ 다섯 명 새 clone·실행 확인
→ 두 흐름의 화면·API·DB 계약 합의
→ 각자 GitHub Issue 작성·상호 검토
→ 견적 2명 / 배차 3명 구현
→ 흐름별 통합 확인
→ 수동 개발 환경 배포·재현
```

`Sprint`, `작업 카드`, `Ready` 같은 용어를 사용하지 않아도 된다. 실제 실행 단위는 GitHub Issue와 PR이다.

## 2. 공통 환경 Issue

### 제목

`팀이 같은 방식으로 프론트·백엔드·MySQL을 실행할 수 있게 한다`

### 결과

다섯 명 모두 새 clone에서 프론트·백엔드를 실행·테스트·빌드하고 MySQL 연결과 JPA 개발 스키마 자동 생성을 확인한다.

### 포함

- 실제 Node·JDK·빌드 도구·패키지 관리자 결정
- 모노레포 프론트·백엔드 골격
- MySQL·JPA 최소 연결과 개발 스키마 자동 생성 확인
- 비밀 없는 환경 변수 예시
- Vercel 개발 환경과 DEV EC2 수동 배포 절차
- 루트·하위 AGENTS.md에 실제 명령 기록

### 제외

- 제품 기능
- 실제 개인정보
- PROD 공개
- 자동 배포·CI/CD

### 완료 조건

- [ ] 다섯 명 모두 새 clone에서 기본 명령을 실행했다.
- [ ] 작성자가 아닌 사람이 문서만 보고 재현했다.
- [ ] 비밀정보가 저장소·로그에 없다.

## 3. 예상 견적 요청 그룹 — 2명

### 공동 결과

```text
사용자가 예상 견적 요청 제출
→ 검토 대기로 저장
→ 운영자가 신규 요청 확인
```

### Issue 1: 견적 FE

- 결과: 사용자가 필수 정보를 제출하고 성공·입력 오류·서버 실패를 이해하며, 운영자는 최소 목록에서 신규 요청을 확인한다.
- 포함: 사용자 폼, 제출 상태, 최소 운영자 목록·빈 상태·조회 실패
- 제외: 가격 자동 계산, 문자 발송, 배차 요청, 회원가입, 결제
- 협업: 견적 BE와 요청·응답 계약을 먼저 작성
- 검토자: 배차 FE
- 완료 증거: 정상·오류 화면, 견적 BE와 연결 결과

### Issue 2: 견적 BE

- 결과: 유효한 예상 견적 요청을 한 건 저장하고 운영자 조회 API로 제공한다.
- 포함: 생성 API, 서버 검증, `검토 대기`, MySQL 저장, 운영자 목록·상세 API, 중복 재시도 기본 처리
- 제외: 가격 판단·문자·배차, 사용자 계정, 배송 도메인 일반화
- 협업: 견적 FE와 계약, 배차 BE와 공통 운영자 인증·DB 충돌 확인
- 검토자: 배차 BE1
- 완료 증거: 정상·4xx·DB 실패·로그 개인정보 테스트. 운영자 인증은 공개 전 별도 Issue로 검증

### 흐름 완료 조건

- [ ] 사용자 제출 한 건이 DB에 저장된다.
- [ ] 운영자 화면에 같은 요청이 나타난다.
- [ ] 입력 오류와 저장 실패를 재현했다.
- [ ] 실제 문자 발송은 운영자의 수동 업무로 남아 있다.

## 4. 배차 요청 그룹 — 3명

### 공동 결과

```text
구매자가 배차 요청 제출
→ 판매자 입력 링크 발급
→ 판매자가 픽업 정보 입력
→ 운영자가 양쪽 정보 확인
```

예상 견적 문자에서 진입하거나 홈에서 바로 시작할 수 있다. 두 경우 모두 새 배차 요청이며 실제 거래 정보를 다시 입력한다.

### Issue 3: 배차 FE

- 결과: 구매자 입력, 판매자 전용 입력과 운영자 최소 확인 화면이 하나의 흐름으로 동작한다.
- 포함: 구매자 폼, 판매자 링크 화면, 판매자 폼, 완료·만료·오류, 운영자 최소 상세
- 제외: 자동 문자, 실제 운송사 배차, 결제, 전체 운영 대시보드
- 협업: 배차 BE1·BE2와 화면별 API 계약을 함께 작성
- 검토자: 견적 FE
- 완료 증거: 구매자→판매자→운영자 정상·오류 화면과 정보 비노출 확인

### Issue 4: 배차 BE1

- 결과: 구매자 배차 요청을 저장하고 판매자만 사용할 입력 링크·세션을 만든다.
- 포함: 구매자 요청 API, 개발 환경용 판매자 링크 식별자 발급·검증, `판매자 입력 대기`, 배차 BE2와 공유할 최소 데이터 경계
- 제외: 판매자 입력 저장의 최종 구현, 실제 문자, 운송사 API, 자동 배차
- 협업: 배차 BE2와 공통 모델·트랜잭션·상태 변경을 먼저 합의
- 검토자: 견적 BE
- 완료 증거: 정상 생성, 잘못된·재사용 링크, 비밀·개인정보 로그 테스트. 실제 만료 정책은 공개 전 DEC-023으로 확정

### Issue 5: 배차 BE2

- 결과: 판매자 입력을 저장하고 운영자가 구매자·판매자 정보를 함께 확인한다.
- 포함: 판매자 입력 API, `최종 검토 대기`, 운영자 조회, 역할별 응답 분리
- 제외: 최종 가격 자동 계산, 문자, 구매자 동의, 실제 배차·운송 상태
- 협업: 배차 BE1과 링크·공통 데이터, 배차 FE와 응답 계약 확인
- 검토자: 배차 BE1
- 완료 증거: 정상 입력, 미인증·다른 역할 접근, 중복 입력, DB 실패, 개인정보 응답 테스트

### 흐름 완료 조건

- [ ] 구매자 요청이 별도 배차 요청으로 저장된다.
- [ ] 판매자 전용 링크를 통해서만 판매자 정보를 입력한다.
- [ ] 운영자가 양쪽 정보를 확인한다.
- [ ] 구매자와 판매자는 서로의 상세주소·연락처를 볼 수 없다.
- [ ] 자동 문자·운송사 API·자동 배차는 없다.

## 5. 각자 Issue에 적을 최소 항목

```text
제목:
완성할 결과:
포함:
제외:
완료 조건:
연결할 화면·API·DB:
담당자:
검토자:
먼저 필요한 작업:
확인 방법과 증거:
```

각자 Issue를 만든 뒤 같은 흐름의 동료와 검토자가 먼저 읽는다. 범위가 합의되기 전에는 구현을 시작하지 않는다.

## 6. PR과 통합

1. Issue 번호로 `develop`에서 작업 브랜치를 만든다.
2. 작은 단위로 구현하고 관련 테스트를 실행한다.
3. PR에 결과·제외·검증·문서 영향을 적는다.
4. 작성자가 아닌 기본 검토자가 확인한다.
5. Merge commit으로 `develop`에 병합한다.
6. 같은 흐름 FE·BE가 개발 환경에서 전체 행동을 함께 재현한다.
7. 두 흐름이 모두 동작한 뒤 수동 배포 절차를 다른 팀원이 재현한다.

## 7. 현재 공개 제한

개발은 명백한 가상 데이터로 진행할 수 있다. 실제 사용자를 받기 전에는 다음을 완료한다.

- DEC-020 개인정보 수집·보관·삭제·안내
- DEC-021 운송 채널·착불·상하차 조건
- 관리자 인증·판매자 링크 만료와 비밀정보 관리
- 운영 주담당·백업 리허설
