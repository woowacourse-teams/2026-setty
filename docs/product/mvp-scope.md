# SETTY MVP 범위

- 상태: **워크북 반영본·팀 대조 검토 필요**
- 기준일: 2026-08-05
- 목표: 최소 제품과 수동 운영으로 예상 견적 수요와 실제 배송 전환을 검증한다.

## 1. MVP 결과 목표

- 유효 예상 견적 요청 5건
- 실제 배송 완료 1건
- 예상 견적 문자 후 종료·배차 요청 전환 기록
- 요청별 가능·불가능, 이탈, 예외와 수동 운영 시간 기록

## 2. 이번 MVP에서 시스템으로 구현

| 사용자·운영 결과 | 구현 범위 |
|---|---|
| 예상 견적 요청 | 필수·선택 입력, 형식 검증, 저장, 접수 결과, `검토 대기` 상태 |
| 운영자 견적 확인 | 인증된 운영자 요청 목록·상세, 판단·가격·문자 발송 결과 기록 |
| 별도 배차 요청 | 문자 링크 또는 홈에서 새 요청 생성, 구매자 실제 거래 정보 재입력 |
| 판매자 정보 취합 | 판매자 전용 링크, 픽업 정보 입력, 구매자에게 완료 여부만 표시 |
| 최종 금액 확인 | 운영자 입력 금액과 구매자 동의·거절 기록 |
| 수동 배차 진행 기록 | 배차·운송·완료·실패·취소 상태와 내부 메모 |
| 역할별 정보 제한 | 구매자·판매자·운영자 응답과 접근 범위 분리 |

예상 견적과 배차 요청은 별도 엔티티·상태로 다룬다. 원본 요청과 전환 요청의 분석 연결은 가능하지만 입력값 자동 복사는 구현하지 않는다.

## 3. 이번 MVP에서 사람이 수행

| 업무 | 사람의 책임 | 시스템 지원 |
|---|---|---|
| 운송 가능 여부·차량 판단 | 운영자가 요청별로 판단 | 판단 근거 조회와 결과 기록 |
| 예상·최종 가격 조회 | 외부 채널에서 직접 확인 | 금액·조회 시각 기록 |
| 문자 발송 | 예상 견적·최종 금액·지연·결과를 직접 발송 | 템플릿과 발송 완료 기록 |
| 판매자 입력 독려 | 직접 연락 | 입력 완료 상태 확인 |
| 착불 배차 | 외부 채널에서 직접 접수 | 배차 상태 기록 |
| 실패·취소·지연 대응 | 당사자·운송자와 직접 협의 | 사유·결과 기록 |
| 배송 완료·인터뷰 | 직접 확인·질문 | 결과와 운영 시간 기록 |

## 4. 이번 MVP에서 제외

- 회원가입과 일반 사용자 계정
- SETTY 내부 결제·수수료·환불
- 자동 가격 계산
- 자동 SMS·알림톡 발송
- 운송사 API
- 자동 배차와 자동 모니터링
- 중고 매물 탐색·등록·판매
- 자체 물류망
- 모든 지역·물품의 운송 가능 보장
- 예상 견적 정보를 배차 요청에 자동 복사
- 미래 확장을 위한 과도한 일반화

## 5. 데이터 확인 후 검토할 후보

- 반복 문자 자동화
- 운영자용 견적 계산 보조
- 운송 가능 여부 판단 체크리스트 보조
- 운송사 API와 대체 운송 채널
- 사용자 계정과 요청 이력
- 내부 결제·정산
- 지역·운송사 확대

## 6. 첫 개발 범위

첫 개발은 공통 환경을 다섯 명이 재현한 뒤 **예상 견적 요청 2명과 배차 요청 3명**으로 나눠 진행한다.

```text
공통 레포·프론트·백엔드·MySQL 실행 확인
→ 예상 견적: 제출 → 저장 → 운영자 확인
→ 배차 요청: 구매자 입력 → 판매자 입력 → 운영자 확인
```

포함:

- 팀원이 동일하게 설치·실행·빌드할 수 있는 공통 환경
- 예상 견적 FE1·BE1 흐름
- 배차 요청 FE1·BE2 흐름
- MySQL·JPA 스키마 자동 생성 저장, 최소 운영자 조회
- 프론트 개발 환경 수동 배포·재현
- 백엔드 DEV EC2 자동 배포 (DEC-026)

제외:

- 자동 가격·문자·운송사 API·자동 배차
- 회원가입·내부 결제
- PROD 공개
- 서버 테스트 CI 게이트, 무중단 배포
- BE 동의 증적·삭제와 운영자 접근 보호 검증 전 실제 개인정보 접수·공개

정형화된 Sprint 기간은 두지 않는다. 각 Issue와 두 사용자 흐름의 완료 조건으로 진행 상황을 판단한다.

## 7. 지금 개발을 시작하려면 먼저 준비할 것

이 표는 첫 기능 Issue를 시작하기 위한 준비를 뜻한다.

| 필요한 준비 | 현재 상태 | 막히는 작업 | 다음 행동 |
|---|---|---|---|
| 실제 Git 저장소와 접근 권한 | **[준비됨]** 실제 레포의 문서 브랜치에 반영 | 문서 승인 전 `develop` 기준 작업 | PR 리뷰 후 `develop` 병합 |
| 견적 2명·배차 3명의 실제 이름 | **[배정됨]** 캐리·밀란 / 스마일·타스·코코 | 각 기능 Issue | 역할표 기준으로 Issue 담당자 입력 |
| 실제 레포와 공통 실행 명령 | **[문서 반영·전원 재현 필요]** | 공통 환경 완료를 전제로 한 기능 Issue | 다섯 명이 새 clone에서 확인 |
| 두 흐름의 화면·API·DB 계약 | **[기능 시작 전 작성]** | FE·BE 통합 | 같은 흐름 담당자가 함께 승인 |
| MySQL 개발 접속 방식 | **[공통 환경 Issue에서 확정]** | BE 저장 작업 | 비밀 없는 로컬·DEV 방식 선택 |
| Vercel·DEV EC2 접근 담당자 | **[담당자 지정 필요]** | 수동 배포 | 권한 보유자와 백업 지정 |

위 항목은 실제 레포에서 공통 환경을 준비하면서 결정·검증할 수 있다. 개인정보·운송 정책 미정은 가상 데이터 기반 개발을 막지 않지만 실제 공개를 막는다.

## 8. 실제 사용자에게 공개하기 전에 확인할 것

다음은 개발 환경 작업은 허용하지만 실제 개인정보를 받거나 배송을 접수하는 공개를 막는다.

| 공개 전 확인 | 담당 | 기한 | 막히는 공개 범위 |
|---|---|---|---|
| 개인정보 수집·이용·보관·삭제·철회 | 밀란 | 실제 사용자 접수 전 | 모든 실제 개인정보 접수 |
| 관리자 접근 보호·비밀정보 공유 방식 | 밀란·백엔드 담당 | 운영 화면 공개 전 | 운영자 화면과 실제 DB |
| 사진 저장 위치·25MB 제한의 보안·비용 검토 | 밀란 | 사진 기능 개발 전 | 실제 사진 업로드 |
| 카카오퀵 제3자 접수·계정 조건 | 캐리 | 배차 요청 공개 전 | 실제 배차 |
| 차량별 가능 물품·규격 | 캐리 | 가능 안내 공개 전 | 가능 여부 보장 |
| 착불 수단·추가 비용 | 캐리 | 최종 금액 안내 전 | 결제·배차 안내 |
| 포장·분해·상하차 가능 범위 | 캐리 | 관련 옵션 안내 전 | 해당 서비스 안내 |
| 거절·취소·지연·운영시간 밖 문구 | 캐리, 팀 리뷰 | 폼 공개 전 | 사용자 안내 |
| 운영 주담당·백업 전체 리허설 | **[담당자 지정 필요]** | 공개 전 | MVP 공개 |

## 9. 범위 변경 규칙

새 입력, 개인정보 노출, 자동화, 외부 서비스, 비용·결제 또는 운영 책임이 바뀌면 구두로 추가하지 않는다. 관련 DEC, 제품 문서와 GitHub Issue를 같은 변경 단위에서 갱신한다.
