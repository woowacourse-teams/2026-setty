# 살아있는 정책 문서 운영 가이드

## 1. 정책의 원본

- 레포의 정책 문서를 **현재 유효한 정책의 원본**으로 둔다.
- 정책 문서에는 현재 팀이 확정한 정책을 기록한다.
- 정책 변경의 이유, 변경안, 영향 범위와 논의는 별도의 정책 변경 Issue에 기록한다. 회의에서 팀 전원이 합의한 결론도 Issue에 남긴다.
- **합의된 변경은 정책 문서에 PR로 반영한다.**
- 정책 문서는 모든 코드 작업의 필수 수정 대상이 아니다. 모든 작업에 정책 확인 절차를 강제하지 않는다. 정책 문서는 “어떻게 구현해야 하지?”에 대한 답이 되는 팀 간 합의 문서다.

## 2. 작업자의 판단 범위

작업자는 기존 공유 정책 안에서 세부 사항을 결정하고 구현한다. 다음 중 하나에 해당하면 공유 정책 변경을 제안한다.

- 기존 공유 정책을 바꿔야 한다.
- 다른 영역의 정책이나 구현에 영향을 준다.
- 앞으로 다른 작업자도 따라야 할 새 기준이 생긴다.

## 3. 작업 유형과 PR 태그

| 유형 | PR 태그 | 처리 |
| --- | --- | --- |
| **정책만 바뀜** | `policy` | 변경안을 제안하고 팀 전원 합의를 받은 뒤 문서 PR로 수정한다. |
| **기존 정책을 구현함** | `implement` | 작업자가 구현한다. 정책 문서 수정이나 정책 재합의는 필요 없다. |
| **코드 동작과 정책이 함께 바뀜** | `policy`, `implement` | 변경안을 먼저 제안한다. 팀 전원 합의 후 문서와 코드를 같은 PR에서 수정한다. |

- `policy`는 **팀이 합의한 정책 문서의 내용을 변경하는 PR**에 붙인다. 일반적인 문서 수정에는 붙이지 않는다.
- `implement`는 **기존 정책을 코드로 구현하거나, 변경된 정책을 코드에 반영하는 PR**에 붙인다.
- 두 태그를 함께 사용하면 정책 변경과 코드 반영이 모두 포함된 것으로 간주한다.

## 4. 정책 변경 절차

1. 정책 변경이 필요해지면 작업자는 정책 변경 Issue를 새로 만든다.
2. 변경안에는 다음을 구분해 적는다.
   - **바꿀 정책:** 현재 규칙 또는 새로 정해야 할 규칙.
   - **어떻게 바꿀 것인가:** 변경 후 규칙, 적용 범위와 시점.
   - **영향받는 정책:** 함께 바뀌거나 충돌 여부를 확인할 규칙.
3. 기존 작업 Issue가 있으면 정책 변경 Issue의 링크만 남긴다.
4. **제안자를 제외한 팀원 전원이 수락**하면 변경을 진행한다. 응답이 없는 상태는 수락으로 간주하지 않는다.
5. 합의 후 제안의 규칙이나 영향 범위가 달라지면 변경된 내용으로 다시 합의한다.
6. 합의된 정책을 문서와 코드에 반영한다. 병합된 정책 문서를 현재 규칙으로 사용하고, 변경 요약과 PR 링크를 팀 공유 채널에 알린다.

## 5. 충돌 관리

- 정책 문서는 주제별로 나눈다. 모든 변경이 한 파일에 모이게 하지 않는다.
- 같은 정책의 변경 제안이 겹치면 먼저 병합된 정책을 기준으로 다음 제안을 다시 검토한다.
- 정책 변경에 의존하지 않는 작업은 합의를 기다리지 않고 진행 후 보고한다.
