# 두 JVM의 점진적 스키마 배포와 데이터 보존 롤백 검증

2026-10-27 로컬에서 컬럼 확장·백필·읽기 전환·수동 앱 롤백·재전환·기존 컬럼 삭제까지 완료했다. 같은 DB에서 최종 매물 6건의 ID와 최신 제목을 보존했고, C3의 V13 DB 재기동·조회·수정도 통과했다.

실험용 앱·마이그레이션·실행 지원 코드는 실험 종료 후 원복했다. 버전별 커밋과 JAR는 보존하며 이 문서와 [결과 원자료 요약](results.json)을 남긴다. 현재 작업 트리의 코드로 실험 DB를 재기동하지 않는다. [재현 절차](REPLAY.md)는 보관한 커밋을 사용하는 별도 로컬 회차를 설명한다.

## 범위와 실행 조건

- 실행 ID: `schema-20261027-01`. DB는 `setty_schema_transition_lab` 하나이며 초기화·DB 복원·역방향 DDL을 수행하지 않았다.
- MySQL 8.4.11, 앱 Temurin 21.0.12.1+1, Nginx 1.28.0. Docker의 독립 JVM 두 개와 동일 DB를 사용했다.
- 호스트 포트: MySQL 13306, Blue 18080, Green 18081, Nginx 18000. 루프백에만 공개했다.
- 외부 JSON 필드는 계속 `title`. 물리 컬럼 `listings.title`을 `display_title`로 옮기는 학습용 변경이다.
- PNG 이미지 저장 대역·알림 `noop`을 사용했다. AWS·dev·prod에는 배포하지 않았다.
- Flyway 검증·Hibernate `validate`를 유지했다. C3 재기동에서도 검증 설정을 우회하지 않았다.

## 확인한 단계와 데이터

| 단계 | 실행과 판정 |
| --- | --- |
| C0·V10 | E1·E2를 실제 등록 API로 생성하고 수정·목록·상세·DB를 대조 |
| C1·V11 | nullable 신규 컬럼 추가, 기존 읽기·양쪽 쓰기. C0·C1이 같은 확장 DB에서 조회·수정됨 |
| 백필 전 | C1이 E1에 양쪽 기록한 뒤 C0가 기존 값만 수정해 불일치 생성. E2 신규 값은 NULL |
| 백필 | C0 종료 후 기존 컬럼 기준으로 NULL·오래된 신규 값 2행 보정. 재실행 변경 0행, 누락·불일치 0 |
| C2·V11 | 신규 읽기·양쪽 쓰기. N1 생성, E1 수정 후 3행 대조 |
| C2 → C1 롤백 | 정상 C2에서 Nginx 경로를 C1로 수동 전환. DB V11, N1 ID·E1 최신 값 유지 |
| 롤백 중 변경 | C1에서 N1 수정·N2 생성. C2 재전환 후 4행과 최신 값 유지 |
| C3·V12 | 기존 컬럼 nullable·앱 참조 제거. 신규 N3의 기존 값은 NULL. C2가 N3를 읽고 수정함 |
| C3 최종 쓰기 | N3의 신규 값만 다시 수정. 기존 값이 오래돼도 C2·C3 모두 신규 값을 읽음 |
| C4·V13 | 기존 컬럼 삭제·신규 컬럼 NOT NULL. C3도 계속 응답, N4 생성 후 6행 대조 |
| C3 재기동 | C4 서비스 중 C3를 V13 DB에 재기동. 전체 조회와 E2 수정 204, C4 재조회 통과 |

각 판정의 시각·슬롯·DB 이력·컬럼·실제 행과 기대값은 `results.json`의 `checkpoints`에서 확인한다. `request_proofs`에는 등록·수정 상태와 서버 요청 ID·실제 upstream을 보존했다.

| 라벨 | 실제 ID | 최종 제목 |
| --- | --- | --- |
| E1 | 1 | `lab-E1-before-rollback` |
| E2 | 2 | `lab-E2-initial` |
| N1 | 3 | `lab-N1-during-rollback` |
| N2 | 4 | `lab-N2-during-rollback` |
| N3 | 5 | `lab-N3-final` |
| N4 | 6 | `lab-N4-final` |

롤백 대상은 양쪽 쓰기를 하는 C1이다. C0는 기존 컬럼만 쓰므로 C2 이후 즉시 복귀 대상으로 사용하지 않았다. C3 이후에는 기존 값이 NULL이거나 오래될 수 있어 C1 복귀를 지원하지 않는다. V13 이후에는 기존 컬럼을 참조하는 C0~C2를 기동하지 않는다.

## 관측 결과와 한계

연속 목록 조회는 **1,757건 모두 HTTP 200·유효한 목록 JSON**이었다. 오류·타임아웃 기록은 0건이다. 요청 완료 후 0.5초 쉬는 단일 관찰기를 사용했으며 정확한 초당 2회 발송기나 운영 용량 시험으로 해석하지 않는다. 구간에는 구현·빌드·테스트 대기 시간도 포함된다.

관찰 범위는 21:19:21.821~21:34:39.865 KST의 요청 시작 시각이다. 전체 표본의 P50은 15.636ms, P95는 34.699ms, 최대는 297.288ms다. 쓰는 중의 모든 표본을 단일 기대 제목과 비교하지 않았고, 값 정합성은 쓰기 완료 후 별도 목록·상세·DB 대조로 판정했다.

C0 환경을 처음 준비할 때 발생한 Docker `Documents` 마운트 접근 거부와 Nginx Host 헤더 오류는 별도로 해결했다. 초기 경로 확인의 HTTP 400 49건은 위 관찰 시작 전 기록이며 무오류 표본에 포함하지 않았다.

C1의 전체 JVM 콘솔 로그는 슬롯 재생성 전 별도 보관하지 못했다. C1 판정은 JAR·Flyway 이력·API 원자료·체크포인트·Nginx 로그를 근거로 한다. C2·C3·C4 로그는 이후 별도 파일로 보관했다. 재현 절차에는 슬롯 재사용 전 `lab logs`를 명시한다.

로컬의 소량 데이터에서 검증한 결과다. 실제 AWS의 배포 스크립트·권한·네트워크·운영 데이터 규모에서의 DDL 시간과 잠금은 추가 dev 리허설이 필요하다. 이벤트 복구·SSE 연결 복구는 이번 실험 범위에 포함하지 않았다.
