# 키워드 구독 알림

키워드를 구독해 두면, 그 단어가 제목에 들어간 매물이 올라올 때 폰으로 알림을 받는다. 이 문서는 어떻게 만들었고, 구독자가 많아도 버티는지 잰 기록이다.

**용어**

| 말 | 뜻 |
|---|---|
| FCM | 구글의 푸시 알림 서비스. 서버가 여기로 보내면 폰에 뜬다 |
| 모의 서버 | 측정할 때 FCM 대신 알림을 받아 주는 가짜 서버. 폰이 1만 대 없어서 쓴다 |
| 발송 완료 | 매물 등록(커밋)부터 구독자 전원에게 보내기를 마칠 때까지 |
| ack | 폰이 알림을 받자마자 서버에 보내는 "받았다" 신호. 도착 시각은 서버 시계로 적는다 |

## 1. 구독과 알림 생성

**문제.** 원하는 매물이 올라와도 알 방법이 없다.

**판단.**
- 제목에 키워드가 들어 있으면 알림을 만든다. 본문·유사어는 보지 않는다.
- 처음 등록할 때만. 수정·재등록은 만들지 않는다.
- 같은 매물·같은 사람은 1건. 판매자 본인은 제외.
- 회원당 키워드는 10개까지.
- 지역 조건은 없다. 배송 거래라 거리는 조건이 아니라 비용이다.

**결과.** 통합 테스트로 확인. dev: 매물 35건 × 구독자 1,000명 → 매물마다 알림 1,000건, 중복·누락 0. 1만 명에서도 10,000건.

## 2. 등록과 발송 분리

**문제.** 등록하면서 구독자에게 한 명씩 보내면 등록 시간이 구독자 수에 비례한다. FCM 응답 0.113초면 9명부터 1초를 넘는다.

**판단.**
- 등록은 매물만 저장하고 커밋한다. 알림 생성·발송은 커밋 뒤 따로 한다(#443·#447).
- 500건씩 묶어 4개 병렬로 보낸다. 500은 FCM 한 번의 최대치다. 높은 우선순위로 보내 절전 중인 폰에도 바로 전달을 시도한다.
- 실패한 건은 1분마다 다시 보내고, 3번 실패하면 멈춘다.
- Kafka·Redis는 안 쓴다. 서버 1대, 월 예산 70달러라 상시 브로커를 둘 수 없다.

**결과.** dev, 기준은 등록 1초 이내(당시 기준).

| 조건 | 등록 응답 | 발송 완료 (평균) |
|---|---|---|
| 분리 전, 1천 명 | 실패 (60초 초과) | 116.9초 |
| 분리 후, 1천 명, 1건씩 | P95 0.18초 | 0.20초 |
| 분리 후, 1만 명, 1건씩 | P95 0.39초 | 0.80초 |
| 분리 후, 1만 명, 동시 10건 | P50 2.15초 | 2천 건만 바로, 나머지 약 12분 |

마지막 줄에서 DB 연결 10개가 바닥났다. 원인과 해결은 4절.

## 3. 실제 폰까지 가는지

**문제.** 모의 서버로는 FCM을 거쳐 폰에 도착하는지 알 수 없다.

**판단.** 발송기를 설정값으로 바꿔 끼운다. `noop`(안 보냄, 기본) / `mock`(모의 서버) / `fcm`(실제) / `mixed`(폰 토큰 있으면 FCM, 없으면 모의 서버. 측정 전용, #473). 폰은 받자마자 ack를 보낸다.

**결과.**

| 조건 | 등록 → 폰 도착 | 서버 발송 → 폰 도착 |
|---|---|---|
| 폰 1대, 35건 (10/12) | 평균 0.42초 | P95 0.59초 |
| 폰 1대 + 구독자 1만 명, 10건 (10/14, `mixed`) | 1.5초 (첫 건 2.9초) | 0.16~0.32초 |

- 10/14: 1만 명 발송 완료 5.7~6.4초, 실패·누락 0, 등록 응답 0.11~0.31초.
- 폰은 가입이 빨라 첫 묶음에 들어갔다. 마지막 묶음이었다면 약 5.7초.
- 폰 1대라 기준값이 아니라 참고값이다. 절전 상태는 보지 않았다.
- 10/11 첫 시도는 무효. Firebase SDK 기본 통신이 응답을 못 읽어 도착한 발송을 실패로 적었다. 통신 방식을 바꿔(#433) 다시 쟀다.

## 4. DB 연결 고갈 해결

**문제.** 1만 명 × 동시 10건에서 DB 연결 10개가 바닥났다.
- 발송 작업이 보내는 내내 연결을 쥐었고, 결과 기록에도 연결이 필요해 서로 기다렸다.
- 알림용 실행기를 추가하면서 Spring 기본 리스너 풀이 사라져 주문·배송·정산 리스너까지 스레드 상한이 없어졌다.
- 등록 트랜잭션이 S3 업로드와 알림 1만 건 INSERT까지 기다렸다.

**판단.**
- 리스너 풀을 나눈다. 공용 2개, 알림 발송 전용 1개(#443).
- 발송 작업은 트랜잭션 없이. 결과 기록할 때만 연결을 잠깐 쓴다. 발송 스레드 8 → 4(#443).
- S3 업로드는 트랜잭션 밖에서. 알림 생성은 커밋 뒤, 다시 실행돼도 중복 없음(#447).

| 쓰는 곳 | 최대 DB 연결 |
|---|---|
| 공용 리스너 | 2 |
| 알림 발송 | 4 |
| 웹 요청 | 나머지 4 이상 |

**결과.** 로컬, 1만 명 × 동시 10건.

| | 고치기 전 | 고친 후 |
|---|---|---|
| DB 연결 타임아웃 | 61건 | 0건 |
| 중복 발송 | 약 13만 5천 건 | 0건 |
| 알림 10만 건 발송 완료 | 15분 넘게 미완료 | 약 40초 |
| 등록 응답 P50 | 0.73~0.85초 | 0.21~0.22초 |
| S3 1초 지연 중 목록 조회 P50 | 1.3초 | 0.1초 |

**한계.** 발송 작업이 1개라 매물이 몰리면 차례로 나가 늦어질 수 있다(5절에서 확인됨).

## 5. 예상 트래픽에서 다시 재기

**문제.** 2·4절은 일부러 무거운 조건이었다. 실제 예상 트래픽에서도 효과가 유지되는지 본다.

**판단.**
- 예상 트래픽: 피크 때 매물 **분당 5건**, 구독자 **1천·1만 명**. 서울에서 한 해 혼자 이사하는 61만~81만 건의 60~80%가 매물 1건을 올린다는 상한(가정) × 피크 배율 5.5배. 계산은 #470 댓글.
- 등록은 무작위 간격으로 10분. 시드를 고정해 고치기 전·후에 같은 시각표(55건)를 쓴다(#473).
- 모의 서버 지연은 FCM dry run 실측 0.874초(500건 × 10회). 0.113초는 빈 요청 왕복이라 너무 낙관적이었다.

| 목표 | 기준 |
|---|---|
| 등록 | 구독자 1천·1만 명의 P95 차이가 같은 조건 반복 차이 안 |
| 발송 | 매물 1건이 12초 안에 완료. 매물이 12초마다 오므로 넘으면 밀린다 |
| 정확성 | DB 연결 타임아웃 0, 중복 발송 0 |

**결과.** 로컬, 고치기 전(`b5cf523`) vs 후(`13b0532`).

| 조건 | 등록 P95 | 발송 완료 P95 / 최대 | 12초 초과 | 타임아웃 / 중복 |
|---|---|---|---|---|
| 전, 1천 명 | 0.116초 | 0.99 / 1.15초 | 0 / 55 | 0 / 0 |
| 전, 1만 명 | 0.248초 | 16.4 / 17.6초 | 11 / 55 | 0 / 0 |
| 후, 1천 명 | 0.106초 | 1.08 / 1.85초 | 0 / 55 | 0 / 0 |
| 후, 1천 명 (반복) | 0.087초 | 1.04 / 1.86초 | 0 / 55 | 0 / 0 |
| 후, 1만 명 | 0.072초 | 12.1 / 15.4초 | 5 / 55 | 0 / 0 |

- 등록: 달성. 고치기 전은 1천 → 1만에서 P95가 2배로 늘었고, 고친 후는 늘지 않았다.
- 발송: 1만 명에서 미달. 매물이 몇 초 간격으로 몰리면 앞 매물(약 5초)을 기다려 12초를 넘는다. 다음 병목.
- 정확성: 달성. 예상 트래픽에서는 고치기 전에도 0이었다. 4절의 고갈은 동시 등록에서만 난다.

**한계.** 내 PC(Docker MySQL, 가짜 S3, 모의 FCM) 값이다. 이사 건수는 범위값이고 "주 사용자 = 혼자 이사"는 가정이다. 10분만 재서 오래 돌려야 보이는 문제는 모른다.
