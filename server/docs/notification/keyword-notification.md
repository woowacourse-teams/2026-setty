# 키워드 구독 알림

## 1. 키워드 구독과 알림 생성

### 문제

* 원하는 매물이 올라와도 사용자가 알 방법이 없다.

### 판단 & 적용

* 매물 제목에 키워드가 들어 있으면 알림을 만든다. 본문·형태소·유사어는 보지 않는다. 이번 과제의 대상은 발송 구조라 매칭은 단순하게 뒀다.
* 처음 등록할 때만 만든다. 수정·재등록은 만들지 않는다.
* 같은 매물·같은 사용자는 1건만. 유니크 키로 막는다.
* 판매자 본인은 자기 매물 알림을 받지 않는다.
* 지역 조건은 두지 않는다. 배송 거래라 거리는 조건이 아니라 비용이다. 카테고리·가격·제외 키워드 칸은 만들어만 두고 비운다.

### 검증 & 결과

* 키워드가 제목에 있는 매물·없는 매물·수정한 매물, 판매자 본인 구독, 대소문자·공백 차이를 통합 테스트로 확인한다.
* dev 측정에서 매물 35건 모두 알림 1,000건 = 구독자 1,000명. 중복 0, 누락 0. 구독자 1만 명에서도 매물마다 10,000건.

## 2. 등록과 발송 분리

### 문제

* 등록 트랜잭션 안에서 구독자에게 한 명씩 보내면 등록 시간이 구독자 수 × FCM 응답 시간이 된다. FCM 응답 0.113초 기준으로 계산하면 9명부터 1초를 넘는다.
* 보내는 동안 DB 연결도 등록 트랜잭션에 묶여, 다른 요청이 연결을 못 받을 수 있다.

### 판단 & 적용

* 등록 트랜잭션에서는 매물만 저장하고 커밋한다. 사진 업로드는 트랜잭션 밖에서 먼저 하고, 알림 행 생성(`INSERT … SELECT`)은 커밋 뒤 발송 작업이 한다(#447).
* 발송은 커밋 뒤 전용 실행기(1개)에서 트랜잭션 없이 한다(`@TransactionalEventListener(AFTER_COMMIT)`, #443). 발송 중에는 DB 연결을 쥐지 않는다. 처리하지 못한 이벤트는 Modulith가 DB에 남기고, 기존 `FailedEventResubmissionScheduler`(1분 간격, 최대 5회)가 다시 실행한다. 아웃박스 테이블은 따로 두지 않는다.
* 500건씩 묶어 보낸다. FCM `sendEach` 한 번의 최대치다.
* 묶음은 전용 스레드 풀(기본 4개)에서 병렬로 보낸다. FCM 연결·응답 대기는 각 10초다.
* FCM은 high priority로 보낸다. 절전(Doze) 중인 기기에도 바로 전달을 시도한다.
* 알림 1건이 3번 실패하면 FAILED로 둔다.
* Kafka·Redis는 쓰지 않는다. 문제는 등록 안에서 발송을 기다리는 것이라 분리로 풀린다. 서버 1대, 월 예산 70달러라 브로커를 상시로 둘 수 없다.

### 검증 & 결과

* **FCM 응답 시간**: dev에서 FCM 주소로 인증 없는 빈 요청을 30번 보내 왕복 시간을 쟀다(응답 401). p50 0.113초, p95 0.129초. 구글 내부 처리 시간은 빠져 있다.
* **가짜 FCM 서버**: 폰 1만 대가 없어 실제 발송 대신, 요청 1번마다 0.113초 뒤 성공을 돌려주는 서버를 dev 안에 띄웠다. 우리 서버는 500건 묶음을 요청 1번으로 보낸다. 실제 FCM은 묶음 안에서도 토큰마다 요청하므로 이 부분은 실제와 다르다. 앱·MySQL과 같은 서버라 측정값은 참고값이다.
* **부하**: 캐리의 Gatling 환경(#408)에 매물 등록 시나리오를 붙였다. PC → dev. 1건씩은 워밍업 5번 + 측정 30번, 동시는 10건을 한꺼번에 1번. 분리 전은 등록 안에서 동기 발송하는 플래그로 쟀다(이후 #447에서 삭제).
* 기준은 등록 응답 1초 이내다.

| 조건 | 등록 응답 | 등록 → 마지막 발송 (평균) |
|---|---|---|
| 분리 전, 1천 명 | 504 (ALB 60초 초과) | 116.9초 (1건) |
| 분리 후, 1천 명, 1건씩 | P50 0.11 / P95 0.18초 | 0.20초 (최대 0.51) |
| 분리 후, 1천 명, 동시 10건 | P50 0.55초 | 0.55초 (최대 0.74) |
| 분리 후, 1만 명, 1건씩 | P50 0.33 / P95 0.39초 | 0.80초 (최대 1.11) |
| 분리 후, 1만 명, 동시 10건 | P50 2.15 / 최대 2.38초 | 직후 2천/10만 건만 발송, 나머지는 1분 간격 재시도로 약 12분 뒤 전부 발송 |

* 1만 명 × 동시 10건에서 DB 연결 10개가 바닥났다. 발송 작업 10개가 시작부터 끝까지 연결을 1개씩 쥐고 있었고, 결과를 기록하는 스레드와 등록 요청이 연결을 못 받았다. DB 연결 타임아웃 분당 최대 261건, dev 알람 2건(DB 연결 타임아웃, 정상 서버 수 부족).
* 1만 명 1건씩에서 35건 중 1건은 묶음 하나가 실패해 58초 뒤 재시도로 나갔다. 원인은 찾지 못했다.
* 10만 명은 측정하지 않았다. 1만 명에서 한계 지점이 나왔다. 등록 시 알림 행 INSERT가 1천 → 1만에서 0.22초 늘어, 10만 명이면 이것만으로 1초를 넘을 수 있다(미측정).
* 구독자 전원에게 1번씩 발송, 등록 응답이 발송을 기다리지 않음, 수정 시 알림 없음, 실패 재시도는 CI 통합 테스트로 확인한다.

## 3. 발송 채널 분리와 실제 기기 도착 확인

### 문제

* 앱이 출시 전이라 FCM으로 대량 발송할 수 없다. 토큰은 앱이 설치된 기기에서만 나오므로 지어낼 수 없다.
* 가짜 서버로는 실제 FCM을 거쳐 기기까지 가는지 알 수 없다.

### 판단 & 적용

* 발송 인터페이스(`NotificationSender`) 하나에 구현체를 바꿔 끼운다. 기본은 아무것도 안 보내는 `noop`, 측정은 `mock`, 앱은 `fcm`. 설정값으로 고른다.
* 측정 전용 `mixed`는 폰 토큰이 있는 회원(실제 폰)에게 FCM으로, 측정용 구독자처럼 토큰이 없는 회원에게 모의 서버로 보낸다. 구독자 1만 명에게 보내는 동안 실제 폰에도 제때 도착하는지 본다(#473).
* 기기는 알림을 받자마자 서버에 ack를 보낸다. 도착 시각은 서버 시계로 기록한다. 기기 시계는 쓰지 않는다.

### 검증 & 결과

* 폰 1대가 구독하고 실제 FCM으로 워밍업 5번 + 30번 보냈다(10/12 00:04, dev). 35건 모두 1번에 발송, 모두 ack.

| 구간 | 값 |
|---|---|
| 서버 발송 → 기기 ack | P50 0.21 / P95 0.59 / 최대 0.78초 |
| 매물 등록 → 서버 발송 | 평균 0.18초 |
| 매물 등록 → 기기 ack | 평균 0.42초 |

* ack 시각에는 기기 → 서버 전송 시간이 들어 있다. 기기 1대라 기준이 아닌 참고값이다. 화면 꺼짐·절전 상태는 따로 보지 않았다.
* 구독자 1만 명과 함께 보낼 때도 폰에 제때 오는지 `mixed`로 쟀다(10/14 12:25, dev). 측정용 구독자 1만 명은 모의 서버(지연 0.874초)로, 폰 1대는 FCM으로 보냈다. 매물 10건, 매물당 알림 10,001건, 실패·누락 0, 등록 응답 0.11~0.31초.

| 구간 | 값 |
|---|---|
| 커밋 → 1만 명 발송 완료 | 5.7~6.4초 |
| 커밋 → 폰 ack | 1.5초 (첫 건 2.9초) |
| 서버 발송 → 폰 ack | 0.16~0.32초 |

* 폰 계정이 측정용 구독자보다 먼저 가입해 알림이 첫 묶음에 들어갔다. 마지막 묶음이었다면 발송 완료 시각(약 5.7초)에 가까웠을 것이다.
* 첫 시도(10/11 23:34)는 무효다. Firebase Admin SDK 기본 통신이 FCM 응답을 `Not in GZIP format`으로 읽지 못해, 기기에 도착한 발송을 실패로 기록했다. 이 실패엔 오류 코드가 없어 우리 코드에서 NPE도 났다. 실패로 기록된 건이 1분마다 재발송돼 DB 연결이 바닥났고 알람이 울렸다. `NetHttpTransport`로 바꾸고 데이터 전용 메시지로 보내도록 고친 뒤(#433) 다시 쟀다.

## 4. DB 연결 고갈 해결

### 문제

* 1만 명 × 동시 10건에서 DB 연결 10개가 바닥났다. 원인 두 가지가 겹쳤다.
  * 발송 작업이 발송 내내 연결을 쥐었다. 결과 기록은 다른 연결이 필요해서, 발송 작업과 결과 기록이 서로를 기다렸다(로컬 로그 `active=10, idle=0, waiting=8`).
  * 알림용 실행기를 추가하면서 Spring 기본 리스너 풀이 만들어지지 않아, 주문·배송·정산 리스너까지 스레드 상한 없이 돌았다(dev 로그 `SimpleAsyncTaskExecutor-26`).
* 등록 트랜잭션이 S3 업로드와 알림 행 생성까지 기다려 연결을 오래 쥐었다.

### 판단 & 적용

* 리스너 풀을 나눈다. 공용 2개(주문·배송·정산, DB만 짧게 쓰는 리스너), 알림 발송 전용 1개(#443).
* 발송 작업은 트랜잭션을 열지 않는다. 발송 스레드는 8 → 4(#443).
* S3 업로드는 트랜잭션 밖에서 하고, DB 저장만 짧은 트랜잭션으로 한다. 결제의 `PaymentService` → `PaymentRecorder`와 같은 구조다(#447).
* 알림 행 생성은 등록 커밋 뒤에 한다. 다시 실행돼도 이미 있는 (매물, 구독자) 알림은 건너뛴다(#447).

| 쓰는 곳 | 최대 DB 연결 |
|---|---|
| 공용 리스너 | 2 |
| 알림 발송 | 4 (결과 기록할 때만 짧게) |
| 웹 요청 | 나머지 4 이상 |

### 검증 & 결과

로컬에서 고치기 전과 후를 같은 조건으로 비교했다.

| 조건 | 고치기 전 | 고친 후 |
|---|---|---|
| 1만 명 × 동시 10건, DB 연결 타임아웃 | 61건 | 0건 |
| 같은 조건, 중복 발송 | 약 13만 5천 건 | 0건 |
| 같은 조건, 알림 10만 건 발송 완료 | 15분 넘게 미완료 | 약 40초 |
| 같은 조건, 등록 응답 P50 | 0.73~0.85초 | 0.21~0.22초 |
| S3 1초 지연, 동시 등록 중 목록 조회 P50 | 1.3초 | 0.1초 |

### 한계

* 내 컴퓨터(Docker MySQL, 가짜 S3·FCM)에서 비교한 값이라 dev 숫자가 아니다.
* 알림 발송 작업이 1개라 매물이 몰리면 차례로 나가 늦어질 수 있다. 발송 작업 수를 늘려도 발송 스레드 4개를 나눠 쓸 뿐이라 빨라지지 않는다.

## 5. 예상 트래픽에서 다시 재기

### 문제

* 2·4절은 1만 명 × 동시 10건이라는 무거운 조건으로 병목을 찾고 고쳤다. 예상 트래픽에서도 고친 효과가 유지되는지 확인한다.
* 모의 FCM 지연 0.113초는 빈 요청 왕복이라, 알림 500건을 한 번에 보낼 때와 다를 수 있다.

### 판단 & 적용

* 예상 트래픽은 피크 때 매물 분당 5건, 구독자 1천·1만 명으로 잡았다. 서울에서 한 해 혼자 이사하는 61만~81만 건(2024년 전입 122만 명 × 1인 이동 79.8%)의 60~80%가 매물 1건을 올린다고 보고(상한) 피크 배율 5.5배를 곱했다. SETTY 주 사용자는 혼자 이사하는 사람으로 가정했다. 근거는 #470 댓글.
* 등록은 응답을 기다리지 않고 무작위 간격으로 10분 보낸다. 시드(470)를 고정해 고치기 전·후에 같은 시각표(55건)를 쓴다(#471).
* 모의 FCM 지연은 FCM dry run으로 500건 × 10회를 보내 잰 p50 0.874초로 바꿨다(#473). PC에서 잰 값이라 dev에서는 더 빠를 수 있다.

| 대상 | 목표 |
|---|---|
| 등록 | 구독자 1천·1만 명의 등록 P95 차이가, 같은 조건을 두 번 잰 차이 안에 든다 |
| 발송 | 매물 1건이 커밋부터 12초 안에 발송을 마친다. 매물이 12초마다 들어오므로 넘으면 밀린다 |
| 정확성 | DB 연결 타임아웃 0건, 중복 발송 0건 |

### 검증 & 결과

로컬에서 고치기 전(`b5cf523`)과 고친 후(`13b0532`)를 같은 조건으로 비교했다. 두 커밋 사이에는 #443·#447만 있다.

| 조건 | 등록 P95 | 발송 완료 P95 / 최대 | 12초 넘은 매물 | DB 연결 타임아웃 / 중복 발송 |
|---|---|---|---|---|
| 고치기 전, 1천 명 | 0.116초 | 0.99 / 1.15초 | 0 / 55 | 0 / 0 |
| 고치기 전, 1만 명 | 0.248초 | 16.4 / 17.6초 | 11 / 55 | 0 / 0 |
| 고친 후, 1천 명 | 0.106초 | 1.08 / 1.85초 | 0 / 55 | 0 / 0 |
| 고친 후, 1천 명 (반복) | 0.087초 | 1.04 / 1.86초 | 0 / 55 | 0 / 0 |
| 고친 후, 1만 명 | 0.072초 | 12.1 / 15.4초 | 5 / 55 | 0 / 0 |

* 등록은 목표를 지켰다. 고치기 전은 구독자 1천 → 1만 명에서 P95가 0.116 → 0.248초로 늘었다(같은 조건 반복 차이 0.019초의 7배). 고친 후는 늘지 않았다.
* 발송은 1만 명에서 목표를 못 지켰다. 고친 후에도 55건 중 5건이 12초를 넘었다(고치기 전 11건). 매물이 몇 초 간격으로 몰린 구간이었고, 발송 작업이 1개라 앞 매물의 발송(약 5초)을 기다렸다.
* 예상 트래픽에서는 고치기 전에도 DB 연결 타임아웃·중복 발송이 0이었다. 4절의 연결 고갈은 동시 10건처럼 등록이 한꺼번에 몰릴 때 생긴다.

### 한계

* 내 컴퓨터(Docker MySQL, 가짜 S3, 모의 FCM)에서 잰 값이다. 가짜 S3는 바로 응답해서 실제 업로드 시간이 빠져 있다.
* 10분만 재서 오래 돌려야 드러나는 문제는 보지 못한다.
* 이사 건수는 1인 외 이동의 인원을 몰라 범위값이다. 주 사용자가 혼자 이사하는 사람이라는 것도 가정이다.
