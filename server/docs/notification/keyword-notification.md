# 키워드 구독 알림

## 1. 키워드 구독과 알림 생성 — 최초 등록 매물을 제목 키워드로 매칭해 알림 생성

### 문제

* 구독·알림 테이블이 없어, 원하는 매물이 등록돼도 사용자가 알 방법이 없다.

### 판단 & 적용

* 매물 제목에 키워드 문자열이 포함되는지로만 매칭한다. 본문·형태소·유사어는 보지 않는다. 매칭 정확도는 낮지만, 이번 과제의 대상은 발송 구조라 매칭 규칙은 단순하게 둔다.
* 최초 등록에만 알림을 만든다. 수정·재등록은 만들지 않는다.
* 같은 매물·같은 사용자 조합은 유니크 키로 막아 1번만 생성한다.
* 지역 조건은 두지 않는다. 배송 거래에서 거리는 조건이 아니라 비용이다. 카테고리·가격·제외 키워드 칸은 만들되 비워 둔다.
* 키워드 알림은 기존 고객 상태·알림 정책에 없는 기준이라 위 규칙을 정책 문서에 반영한다.

### 검증 & 결과

* 키워드가 제목에 있는 매물·없는 매물·수정한 매물을 등록해 알림 생성 여부를 검증할 예정이다.
* 매물 1건당 생성된 알림이 해당 키워드 구독자 수와 같은지, 중복·누락이 0건인지 확인한다. 결과: 알림 [실측값]건 / 구독자 [실측값]명, 중복 [실측값]건, 누락 [실측값]건.

## 2. 등록·발송 분리 — 구독자 수와 무관하게 등록 응답 유지

### 문제

* 등록 트랜잭션 안에서 구독자를 순회하며 외부 발송을 동기 호출하면, 등록 응답 시간이 구독자 수 × 외부 지연이 된다. 외부 지연을 50ms로 가정하면 구독자 20명에서 1초를 넘는다.
* 발송하는 동안 DB 연결이 트랜잭션에 묶여, 다른 요청의 연결 획득이 밀릴 수 있다.

### 판단 & 적용

* 등록 시 알림을 한 번에 INSERT하고 커밋한다. 발송은 Modulith 이벤트 리스너가 커밋 후 비동기로 처리한다. 미완료 발행 기록은 재시작 시 재발행되므로 아웃박스 테이블을 따로 두지 않는다. 처리 완료된 기록은 삭제되므로 발송 시각과 결과는 알림 테이블에 남긴다.
* 발송은 500건씩 묶어 발송 포트를 호출한다. FCM 멀티캐스트 상한에 맞춘 값이다.
* 묶음은 전용 스레드 풀에서 병렬로 보낸다. 구독자 10만 명이면 묶음이 200개라, 순서대로 보내면 마지막 구독자가 늦어진다. 병렬 수는 측정으로 정한다.
* FCM은 high priority로 보낸다. 일반 우선순위는 절전 중인 기기에서 전달이 지연된다.
* 실패분은 3회 재시도 후 실패로 표시한다. 재시도 횟수는 알림 상태로 직접 관리하고, 실패한 이벤트 재발행은 기존 `FailedEventResubmissionScheduler`(1분 간격, 최대 5회)를 그대로 쓴다.
* Kafka·Redis는 도입하지 않는다. 병목은 등록 안의 동기 호출이라 큐로 풀리는 문제가 아니다. 서버 한 대로 운영하면서 브로커를 상시 띄우는 것은 스프린트 1에서 관측 서버를 줄인 결정과도 반대이고, 월 예산 안에서 상시 서버를 더 두기 어렵다.

### 검증 & 결과

* 외부 지연은 실측한다. dev EC2에서 FCM API 왕복 시간과 500건 묶음 1회 발송 시간을 재고, 그 값을 모의 푸시 서버의 지연으로 쓴다.
* 부하는 캐리의 Gatling 환경(`server/performance`, #408)에 매물 등록 시나리오를 추가해 건다. 구독자 수를 1천 → 1만 → 10만으로 늘리며 매물 1건 등록과 매물 10건 동시 등록을 측정할 예정이다. 분리 전 값은 동기 발송 플래그로 실측한다. 구독자 시드는 `server/performance/fixtures` 규칙(preflight → ROLLBACK 시험 → COMMIT → cleanup)을 따른다. DB 연결 대기와 타임아웃은 기존 커넥션 풀 지표(#331)로 수집한다.
* Gatling은 캐리와 같이 개발자 PC에서 dev를 향해 실행한다. 모의 푸시 서버는 dev EC2가 프라이빗 서브넷이라 PC에 둘 수 없으므로 VPC 안에 둔다(t4g.micro 신설 또는 dev 안, 미결). 발송 로그는 묶음 단위로만 남겨 로그 비용을 억제한다.
* 기준은 등록 응답 1초 이내로 둔다. 구독자 수를 늘리며 1초를 넘기 직전의 구독자 수를 분리 전 [실측값]명, 분리 후 [실측값]명으로 기록할 예정이다.
* 발송 완료 시간은 합격 기준 없이 구독자 수별로 기록한다. 1천/1만/10만 명에서 커밋부터 마지막 발송까지 [전후 실측값]초, 첫 발송과 마지막 발송의 차이 [전후 실측값]초. 모의 푸시 서버가 요청별 수신 시각을 기록한다.
* 같은 구독자 수에서 등록 API P95 [전후 실측값]ms, DB 연결 대기 최대 [전후 실측값]건, 타임아웃 [전후 실측값]건을 기록할 예정이다.
* 구독자 전원에게 정확히 1회 발송, 등록 응답이 구독자 수와 무관함, 수정 시 알림 없음은 CI 테스트로 확인한다.

## 3. 발송 채널 분리와 수신 확인 — 채널을 바꿔 끼우고, 실제 기기 도착 확인

### 문제

* 앱이 출시 전이라 FCM으로 대량 발송할 수 없다. 토큰은 설치된 앱마다 구글이 발급하는 주소라 지어낼 수 없고, 가짜 토큰은 에러로 돌아온다.
* 서버 발송만으로는 실제 FCM 경로로 기기에 도착하는지 확인할 수 없다.
* 기존 SSE는 배송 요청 전용이고 연결을 사용자 단위로 식별하지 않아, 특정 구독자에게만 보낼 수 없다.

### 판단 & 적용

* 발송 포트 하나에 구현체를 나눈다. 접속 중 사용자는 SSE, 부하 측정은 모의 서버, 앱은 FCM이다(안드로이드가 Firebase를 연동하면 추가). 병목은 서버 발송 구조에 있으므로 외부 채널은 바꿔 끼울 수 있어야 한다. SSE에는 사용자 단위 연결 관리를 새로 둔다.
* 앱은 수신 즉시 ack를 보내고, 서버는 ack를 받은 시각을 서버 시계로 기록한다. 기기 시계는 쓰지 않는다.

### 검증 & 결과

* 실기기 1대와 에뮬레이터를 같은 키워드로 구독시키고 매물 등록을 30회 반복해(P95를 내기 위한 최소 표본), 서버 발송 완료부터 기기 수신까지 P50·P95 [실측값]초를 기록할 예정이다. 표본이 적어 기준으로 쓰지 않고 참고값으로 남긴다. 안드로이드 연동이 안 되면 다음 스프린트로 넘긴다.
* 채널 구현체를 바꿔도 2번 측정값이 유지되는지 확인한다.

## 하지 않는 것

* 지역·카테고리·가격 조건 구현 → 다음 스프린트
* 형태소·유사어 매칭 → 알고리즘 문제
* 구매 신청·선점 부하 → 이번 범위 밖
* 기기 도착 시각 맞추기 → 꺼진·오프라인·절전 기기의 도착은 서버가 통제할 수 없다. 필요하면 예약 공개·추첨 같은 제품 정책으로 다룬다.
* Flyway 적용

## 갱신 조건

* 서버 1대의 한계가 측정되면(병렬 수를 올려도 발송 시간이 줄지 않는 지점), 다음 단계(Kafka·서버 2대 + Redis Pub/Sub) 비교 실험을 검토한다. 이번 측정값을 기준선으로 같은 부하에서 비교하고, 실험 서버는 실험할 때만 켠다.

## 정하지 않은 것

* 모의 푸시 서버 위치: t4g.micro 신설 vs dev EC2 안(참고값 처리)
* 테이블 파일: `schema/notification.sql` 신설 추천(코드도 `setty.notification` 최상위 모듈). 대안은 `schema/platform.sql`에 추가
