# 로컬 SSE 1,000개 연결 검증 결과

**로컬에서 SSE 연결 1,000개를 45초 유지했고, 상한 초과 거부와 연결 정리 후 재접속이 통과했다.** 이 결과는 해당 로컬 환경의 연결 유지 검증이며 dev·운영 용량을 확정한 결과가 아니다.

## 실행 조건

- 실행일: 2026-10-13, 12:57~13:00 KST.
- Spring 애플리케이션: `3aa2795`, Java 21.0.5, 힙 초기 128MiB·최대 512MiB.
- 대상: `http://127.0.0.1:18080`, 단일 Spring Boot 프로세스. 부하 생성기와 같은 macOS PC를 사용했다.
- DB: 전용 포트의 MySQL 8.4.11 컨테이너, 임시 `setty_sse_probe` DB. 기사 1,002개의 테스트 인증 데이터를 준비했다.
- 연결: 기사당 1개씩 20초에 걸쳐 1,000개를 만들고 목표 도달 후 45초 유지했다. 기사별 상한은 2개, 전체 상한은 1,000개다.
- 변경 이벤트 X=0. heartbeat를 유지하고 목록 API를 약 500ms 간격으로 조회했다. 모든 기사 앱이 동시에 목록을 조회하는 조건은 아니다.

## 서버 메모리 표본

`ps`의 프로세스 RSS와 `jcmd GC.heap_info`의 힙 사용량을 수집했다. 아래 값은 해당 구간의 표본이며 모든 순간의 최댓값은 아니다. 강제 GC는 실행하지 않았다.

| 구간 | 힙 사용량 | 프로세스 RSS |
| --- | ---: | ---: |
| 기준값: 본 부하 이전 | 72.7MiB | 148.0MiB |
| 1,000개 유지 구간: 표본 최댓값 | 182.5MiB | 256.4MiB |
| 전체 연결 종료·31초 대기 후 | 224.2MiB | 201.4MiB |

종료 후 힙이 기준값으로 돌아오지 않았다는 사실만으로 누수라고 판단하지 않는다. 자연 GC 시점과 비교 가능한 상태를 맞추지 않았으므로 연결당 메모리 크기나 영구 누수 여부를 확정하지 않는다.

## 연결 정리와 검증 한계

첫 실행에서는 초기 점검 연결을 닫은 뒤 16초만 기다려 본 부하의 첫 연결이 429로 거부됐다. TCP 종료 직후 또는 heartbeat 한 번 뒤에 서버 연결이 반드시 제거된다는 가정이 맞지 않았다. 스크립트는 준비·종료 대기를 31초, 복구 대기를 최대 40초로 변경했다. 본 부하에서 관측한 약 24.4초의 복구 시간도 정상 heartbeat 전송을 통한 단절 확인을 포함한다.

기능 판정은 통과했지만 수치 SLO는 정하지 않았다. API 지연과 메모리는 관측값으로 보고하며, dev의 프록시·사양·기존 연결과 같은 PC에서 실행한 부하 생성기의 영향을 별도로 확인해야 한다. 실제 기사 앱 화면, 변경 이벤트 처리량과 120초 만료 이후 장시간 재접속은 이번 범위에 포함하지 않았다.
