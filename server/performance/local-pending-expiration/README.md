# 대기 주문 만료 처리 개선 실험

## 브랜치와 실행 전 확인

이 디렉터리는 #461의 실험 도구다. 묶음 구현과 일반 CI 회귀 테스트는 #460에서 별도로 관리한다.
아래 수치는 2026-10-13 원래 실험 체크아웃의 기록이며 최신 develop의 재측정 수치가 아니다.
기준값 실험은 구현 병합 전에도 실행할 수 있다. 묶음 크기·잠금 실험은 #460 구현이 있는 코드에서
`-Dexpiration.benchmark.batch=true`를 지정해야 컴파일·실행된다. 이 옵션 없이 전체 실험을
자동 실행하지 말고 아래처럼 대상 테스트를 하나씩 지정한다.

최신 develop의 목록 API는 cursor/size 없이 호출하면 전체 목록을 반환하므로 기존 HTTP 입력을
유지한다. 이후 계약 변경 시 반환 건수와 데이터 준비를 먼저 점검한다.


만료 주문을 한 건씩 처리하던 경로를 묶음 처리로 변경했고, 현재 기본 묶음 크기는 200건이다. 500건과 1,000건의 만료 대상에 대해 처리 시간, 잠금 유지 범위, 같은 매물의 실제 주문 API를 비교해 선택했다. 그 과정에서 다른 매물의 주문 INSERT까지 막는 인덱스 전체 스캔을 발견해 PK 인덱스 힌트로 보완했다. 만료 500건의 정상 경로에서 SQL은 기존 2,001회에서 13회로, 트랜잭션은 500회에서 3회로 줄어든다. 이전의 100·200·500건 선택 기록은 당시 조건의 측정 이력이며, 현재 선택 근거는 아래의 잠금·HTTP 실험이다. 이 결과는 만료 작업 자체의 비용 감소이며 사용자 API 응답 속도 향상을 뜻하지 않는다.

## 부하 규모와 검증 목표

실사용자가 없는 프로젝트의 합성 설계 용량으로 재고 5,000개 중 10%인 500개에 짧은 피크 동안 주문이 생긴다고 가정했다. 실제 유입 예측이나 관측치가 아니다. 주문의 60%가 결제되지 않는 가정에서는 300건, 전부 결제되지 않는 보수적 조건에서는 500건이 만료된다. 300건이 6분에 걸쳐 나뉘면 한 번에 50건을 처리한다. 60%도 관측된 이탈률이 아닌 시나리오 입력값이다.

변경 전후 모두 재고 5,000개와 주문 500건을 사용한다. 만료 대상 300건의 나머지 200건은 결제 확정 상태로 보존한다. 분산 시나리오는 실제로 6분을 기다리지 않고 고정 Clock을 1분씩 진행한다. 6분 만료와 처리 종료 후 1분 대기하는 운영 스케줄 설정은 변경하지 않는다.

최초 100건 구현의 개선 가설은 정상적인 500건 처리에서 SQL을 21회, 트랜잭션을 5회로 줄이면서 주문과 매물 상태의 정확성을 유지하는 것이었다. 이를 검증한 뒤 묶음 크기를 비교했다. 현재 200건 선택은 500·1,000건 조건의 처리 비용과 잠금 범위를 함께 고려한 판단이며, 모든 부하와 경합 상황의 최적값이라고 주장하지 않는다.

## 처리 방식과 동시성

1. 스케줄러가 실행 시작 시각을 기준으로 만료 후보 ID를 조회한다.
2. 최대 200개씩 주문 행을 ID 순으로 잠그고 `Order.canExpire`로 현재 상태를 재확인한다. 후보 조회 뒤 결제가 확정된 주문은 제외한다.
3. 대상 주문을 일괄 만료하고, 그 주문에 해당하는 매물을 잠근 뒤 선점을 일괄 해제한다. 두 변경은 같은 트랜잭션에서 커밋한다.
4. 묶음 처리가 실패하면 전체를 롤백한 뒤 기존 단건 경로로 재시도한다. 한 건의 오류가 나머지 정상 주문을 막지 않게 한다.

정상 경로는 후보 조회 1회와 묶음별 주문 잠금·주문 변경·매물 잠금·매물 변경 각 1회다. 모든 후보가 여전히 만료 대상이고 선점된 매물인 경우 SQL은 `1 + 4 × ceil(N / 200)`회다. SQL 집계에 커밋과 연결 제어 메시지는 포함하지 않는다. 실제 변경되는 데이터 행 수는 여전히 주문 N개와 해당 매물 N개다.

한 건씩 커밋하던 방식보다 동시에 잠그는 행 수는 많아진다. 묶음 대상을 최대 200건으로 제한하지만 같은 매물에 대한 변경은 해당 묶음이 커밋될 때까지 기다릴 수 있다. 신규 주문 요청은 앞선 기존 주문 조회에서 아직 PENDING인 주문을 보고 거절될 수도 있다. 묶음 오류로 단건 재시도가 발생하면 정상 경로의 SQL 감소 수치는 적용되지 않는다. 전체 후보 ID를 한 번에 조회하는 기존 방식은 유지한다.

일괄 변경 후 영속성 컨텍스트를 비워 이전 상태가 남지 않게 한다. 매물의 판매 상태와 삭제 상태는 유지하고, 이미 선점이 풀린 매물의 수정 시각도 바꾸지 않는다. 만료된 주문 기록을 보존하며 새 주문의 선점을 이전 만료 후보가 해제하지 않도록 한다.

## 최초 100건 구현의 전후 측정

환경은 Java 21.0.12.1, Testcontainers MySQL 8.4.11이다. 같은 Mac에서 동일한 `PendingExpirationWorkloadTest`를 변경 전후 각각 실행했다. 300건과 500건은 각각 3회, 분산 50건은 6회 스캔을 3회 반복했다. 아래 시간은 중앙값이다.

| 한 번의 만료 대상 | SQL 전후 | 트랜잭션 전후 | 처리 시간 전후 |
| --- | --- | --- | --- |
| 50건 | 201 → 5 | 50 → 1 | 168.3ms → 12.2ms |
| 300건 | 1,201 → 13 | 300 → 3 | 1,335.0ms → 59.7ms |
| 500건 | 2,001 → 21 | 500 → 5 | 2,040.2ms → 96.5ms |

500건 처리 시간은 약 95.3% 감소했다. 개선 후 3회 범위는 72.7~286.8ms로 로컬 실행 변동이 있으므로 중앙값 하나를 운영 성능 보장으로 쓰지 않는다. 모든 측정에서 만료 대상 처리, 미래 만료 주문·결제 확정 주문 보존, 선점 해제, 무관한 매물 상태를 검증했다.

원자료는 저장소 루트의 `performance-results/pending-expiration/improvement-20261013/`에 있다. `before/`와 `after/`의 `samples.json`이 개별 측정값이고 `comparison.json`이 집계다. 변경 전 소스는 `before/source/`에 보존했다.

## 1차 50건 100건 200건 비교

재고 5,000개와 만료 주문 500건을 동일하게 준비하고 크기별로 예열 3회와 본 측정 12회를 수행했다. 세 크기의 실행 순서 6가지를 각각 2회 사용해 먼저 실행되는 이점을 고르게 나눴다. 운영 코드의 후보 조회와 트랜잭션 서비스를 그대로 사용하고, 테스트 반복문에서 묶음 크기만 바꿨다. 픽스처 초기화와 상태 검증 시간은 측정에서 제외했다.

| 묶음 크기 | 전체 처리 중앙값 | 첫 묶음 확정 중앙값 | 매물별 평균 해제 시점의 중앙값 | SQL | 트랜잭션 |
| --- | --- | --- | --- | --- | --- |
| 50건 | 89.0ms | 10.4ms | 51.2ms | 41회 | 10회 |
| 100건 | 53.9ms | 12.1ms | 32.6ms | 21회 | 5회 |
| 200건 | 42.3ms | 17.4ms | 28.2ms | 13회 | 3회 |

200건은 100건보다 전체 처리가 12회 모두 빨랐고, 같은 회차끼리 비교한 차이의 중앙값은 13.0ms였다. 각 실행에서 매물 수로 가중한 평균 해제 시점도 12회 모두 빨랐다. 이 세 후보 중에서는 200건을 선택했으며, 이후 확대 비교에서는 잠정 500건을 적용했고, 잠금·HTTP 검증을 거쳐 현재 200건으로 다시 선택했다. 200건은 100건보다 SQL이 8회, 트랜잭션이 2회 줄어든다.

대신 첫 묶음 확정은 같은 회차 비교에서 중앙값 5.2ms 늦어졌고, 한 번에 잠그는 주문 수는 100개에서 200개로 늘어난다. 각 실행의 가장 긴 묶음 트랜잭션 시간 중앙값은 100건에서 11.6ms, 200건에서 16.3ms였다. 같은 행을 두고 경쟁하는 HTTP 부하에서는 별도 확인이 필요하다.

해제 시점은 커밋이 끝난 서비스 호출의 반환 시각으로 계산했다. 매물별 평균은 각 묶음의 반환 시각에 처리 건수를 곱해 합한 뒤 500으로 나눈 값이다. 실제 사용자 응답 시간이나 개별 행의 정확한 잠금 유지 시간을 측정한 값은 아니다. 실제 1분 스케줄 대기도 포함하지 않는다.

이 실험의 100건 처리 시간 53.9ms와 앞선 전후 실험의 96.5ms는 예열 횟수와 측정 구성이 다르므로 섞어 비교하지 않는다. 원자료는 `performance-results/pending-expiration/batch-size-20261013/`의 `samples.json`, `metadata.json`, `summary.json`에 있다.

선택한 200건 설정을 실제 스케줄러에도 적용하고 기존 `PendingExpirationWorkloadTest`로 다시 확인했다. 만료 대상 50·300·500건의 상태 검증이 모두 통과했으며 SQL은 각각 5·9·13회, 트랜잭션은 1·2·3회였다. 이 검증에서 500건 처리 중앙값은 79.1ms였고, 예열과 실행 구성이 다른 크기 비교 실험의 42.3ms와 구분한다. 원자료는 `batch-size-20261013/selected-200/`에 있다.

## 과거 200건부터 500건까지 확대 비교: 전체 처리 시간만으로 잠정 선택

같은 만료 주문 500건에 대해 200·300·400·500건 묶음을 비교했다. 각 크기의 예열 3회와 측정 12회, 실행 위치와 인접 실행 순서 균형을 유지했다. 500건이면 모든 대상이 한 묶음에 들어가므로, 이 부하에서 500건보다 큰 상한은 묶음 수와 SQL 수를 더 줄이지 못한다.

| 묶음 크기 | 전체 처리 중앙값 | 첫 묶음 확정 중앙값 | 매물별 평균 해제 시점의 중앙값 | SQL | 트랜잭션 |
| --- | --- | --- | --- | --- | --- |
| 200건 | 46.8ms | 17.8ms | 29.9ms | 13회 | 3회 |
| 300건 | 37.2ms | 21.6ms | 27.7ms | 9회 | 2회 |
| 400건 | 37.0ms | 25.0ms | 27.4ms | 9회 | 2회 |
| 500건 | 29.1ms | 29.1ms | 29.1ms | 5회 | 1회 |

500건은 12회 모두 전체 처리가 가장 빨랐고 SQL과 커밋 횟수도 가장 적었다. 300건과 400건은 둘 다 두 묶음이며 전체 시간 차이도 작았다. 당시에는 전체 정리 비용 감소를 우선해 500건을 잠정 적용했다. 그러나 대상 500건은 가정한 실험 규모일 뿐 서비스 최대치가 아니며, 이를 근거로 묶음 500건이 적절하다고 확정한 결론은 철회했다. 이후 아래 잠금·동시 주문 실험을 통해 현재 200건으로 변경했다.

500건은 첫 해제까지 전부 기다려야 한다. 200건 대비 첫 해제는 같은 회차 비교에서 중앙값 11.1ms 늦어졌고, 매물별 평균 해제 시점 차이는 중앙값 0.3ms 정도로 작았다. 따라서 500건이 모든 매물을 더 일찍 풀어 준다고 주장하지 않는다. 한 번에 잡는 잠금 수와 실패 시 롤백 범위도 증가한다. 빠른 일부 해제나 같은 행에 대한 경합이 더 중요한 환경에서는 작은 묶음이 유리할 수 있다.

이 결과는 하나의 로컬 MySQL에서 정상 처리만 비교한 것이다. 다른 서버 사양과 경합 부하의 최적값을 보장하지 않는다. 1차 비교와 프로세스·예열 구성이 다르므로 두 표의 시간을 섞어서 순위를 매기지 않는다. 원자료는 `performance-results/pending-expiration/batch-size-extended-20261013/`에 있다.

선택한 500건 설정은 실제 스케줄러와 기존 부하 테스트로도 확인했다. 만료 대상 50·300·500건 모두 SQL 5회와 트랜잭션 1회였으며, 미래 만료 주문과 결제 확정 주문을 보존하는 상태 검증이 통과했다. 이 별도 검증의 500건 처리 중앙값은 46.5ms였다. 크기 비교 실험은 예열과 실행 구성이 달라 위 표의 29.1ms와 구분한다. 원자료는 `batch-size-extended-20261013/selected-500/`에 있다.

## 현재 선택: 잠금 유지 시간과 같은 매물 HTTP를 함께 비교

**200건을 기본값으로 선택했다.** 전체 처리 시간만 최소화하면 이번 후보 중 500건이 빠르다. 다만 100→200건에서 얻는 큰 처리 비용 감소를 확보하고, 그 이후의 추가 이득보다 한 번의 잠금 시간·잠금 대상 수·실패 시 롤백 범위를 작게 유지하는 쪽을 택했다. 운영 SLO나 수학적으로 유일한 최적값을 입증한 것은 아니다.

재고 5,000개, 만료 대상 500건과 1,000건, 묶음 크기 50·100·200·300·400·500건을 비교했다. 500건은 기존의 가정한 실험 규모이고 서비스 최대치가 아니다. 1,000건은 같은 주문 집단을 두 배로 늘린 민감도 확인 조건이며 실제 유입 예측이 아니다. 각 조건에서 HTTP 없음/있음을 각각 12회 측정했다(총 288회). 크기별 실행 위치와 인접 순서를 균등하게 배치했고, 각 크기의 예열은 500건+HTTP 조건에서 3회였다.

아래는 **쿼리 보완 후, 같은 매물 HTTP 요청이 있는 조건**이다. 처리 시간은 실행별 중앙값, 잠금 범위는 각 실행에서 가장 긴 묶음의 유지 시간 하한·상한을 각각 구한 중앙값이다.

| 50 | 73.0ms | 5.1~7.6ms | 1.7~4.6ms | 145.6ms | 5.7~8.5ms |
| 100 | 46.0ms | 6.1~8.9ms | 2.1~5.1ms | 93.2ms | 7.9~10.6ms |
| **200** | **37.9ms** | **9.3~12.6ms** | **3.2~6.6ms** | **64.3ms** | **10.4~13.1ms** |
| 300 | 31.1ms | 12.3~15.2ms | 4.3~7.7ms | 59.7ms | 12.8~16.2ms |
| 400 | 29.0ms | 14.5~17.5ms | 5.0~8.3ms | 52.4ms | 14.5~17.4ms |
| 500 | 23.3ms | 17.8~20.8ms | 6.1~9.4ms | 48.2ms | 18.7~22.2ms |

잠금 획득을 DB 내부의 행별 시각으로 관찰한 것은 아니다. JDBC의 `SELECT ... FOR UPDATE` 시작·종료와 `commit()` 시작·종료를 계측했다. 잠금은 SELECT 실행 중 획득되고 COMMIT 실행 중 해제되므로, `[커밋 시작 − SELECT 종료, 커밋 종료 − SELECT 시작]`로 유지 시간을 감쌌다. 기본 버퍼링 JDBC 결과를 사용하며, 범위에는 네트워크·드라이버 왕복의 불확실성이 있다. 트랜잭션 시작·연결 획득부터 전부 잠금 시간으로 계산했던 이전 대용 지표보다 좁은 범위다. 신뢰구간이나 운영 최대 지연으로 해석하지 않는다.

선택에서 포기한 이득도 명시한다. 200→500건으로 키우면 전체 처리 중앙값이 500건 조건에서 14.5ms, 1,000건 조건에서 16.0ms 줄어든다. 대신 주문 잠금 유지 상한의 중앙값은 각각 12.6→20.8ms, 13.1→22.2ms로 길어지고 한 묶음의 대상은 2.5배가 된다. 500건 조건의 첫 해제 시점도 13.7→23.3ms로 늦어진다. 200건이 모든 지표에서 우세하다는 결론은 아니다.

같은 회차를 짝지어 비교해도 경향은 유지됐다. 100→200건의 처리 시간 차이 중앙값은 500건에서 -11.1ms(12회 중 11회 감소), 1,000건에서 -28.0ms(12회 모두 감소)였다. 200→300건의 차이는 각각 -7.4ms와 -5.7ms였다. 같은 회차 차이의 중앙값과 표에 있는 두 중앙값의 차이는 계산이 다르므로 구분한다. 원자료에는 모든 값과 사분위수·최솟값·최댓값을 보존했다.

### 같은 매물의 실제 주문 요청

속도 측정에서는 첫 묶음과 마지막 묶음의 주문 잠금 조회가 끝난 직후, 해당 매물에 실제 `POST /api/orders`를 하나씩 비동기로 보냈다. 만료 작업을 인위적으로 멈추지 않았다. HTTP 스레드의 기존 주문 확인 SQL과 만료 트랜잭션의 커밋 시각도 기록했다.

- 자연 실행 요청 288건 중 281건은 기존 주문 확인 SQL이 커밋 시작 전에 끝났고, 7건은 커밋 호출 구간과 겹쳤다. 전부 `400 ALREADY_ORDERED`였으며 매물 잠금 SQL까지 도달하지 않았다.
- 전체 만료 작업이 끝난 뒤 재시도한 288건은 모두 `201`이었고, 새 PENDING 주문·6분 기한·매물 선점 상태를 DB에서 검증했다.
- 별도 관찰 실험에서는 매물 UPDATE 후 커밋 직전에 래치로 멈췄다. 여섯 크기 모두 커밋 허용 전에 같은 매물은 400, 다른 매물은 201이 완료됐고, 커밋 후 같은 매물의 재요청은 201이었다. 이 의도적 대기 시간은 위 성능 표에 포함하지 않았다.

따라서 같은 매물의 재주문은 잠금이 풀릴 때까지 자동 대기·성공하는 구조가 아니다. 커밋 전에는 기존 PENDING 주문을 보고 거절하며, 커밋 후 새 요청이 필요하다. 두 HTTP 요청은 정확한 동시 상황을 확인하는 탐침이며 최대 처리량 부하나 실제 재시도 행동을 대표하지 않는다. API 응답 속도가 개선됐다는 결론도 내리지 않는다.

### 실험 중 발견한 추가 병목과 보완

기존 묶음 쿼리에서 만료 대상 500건 중 200·300·400건을 처리할 때, 같은 매물은 즉시 거절됐지만 다른 매물 4999의 주문 INSERT가 만료 커밋을 기다렸다. 의도적으로 만료 커밋을 보류한 상태의 `performance_schema.data_lock_waits`에 다음 대기가 기록됐다.

- 대기: `orders.PRIMARY`, `X,INSERT_INTENTION`, `supremum pseudo-record`
- 차단: `orders.PRIMARY`, `X`, `supremum pseudo-record`
- 실행 계획: 주문 잠금 SELECT와 UPDATE가 `type=index`, 예상 검사 행 500인 전체 인덱스 스캔

즉 대상 ID만 잠그는 것으로 생각했던 쿼리가 인덱스 끝의 삽입 구간까지 잠갔다. 관찰 중 50·100·500건에서는 다른 매물이 성공했지만, 이것이 특정 크기의 영구적 안전성을 뜻하지 않는다. 실행 계획은 데이터 비율과 통계에 따라 달라진다. MySQL의 잠금은 WHERE 결과뿐 아니라 검사한 인덱스 범위의 영향을 받는다. [MySQL 공식 잠금 설명](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html?ff=nopfpls)

주문·매물의 묶음 잠금 SELECT와 묶음 UPDATE에 MySQL `FORCE INDEX (PRIMARY)`를 적용했다. 진단 시 200·300·400건의 대안 계획은 각각 `type=range`, 예상 검사 행 200·300·400이었다. 보완 후 여섯 크기 모두 다른 매물 주문이 커밋 보류 중에도 완료됐다. 새 인덱스나 테이블 변경은 없다. 힌트는 MySQL 전용이며 모든 미래 데이터에서 실행 계획을 보장하지는 않으므로 데이터 분포가 크게 바뀌면 다시 확인한다.

원자료는 저장소 루트의 다음 폴더에 있다.

- `performance-results/pending-expiration/contention-20261013/`: 최초 288회 측정. 뒤이은 관찰 실험에서 다른 매물 주문이 대기하여 테스트 전체는 실패했으므로 최종 통과 결과로 사용하지 않는다.
- `performance-results/pending-expiration/contention-probes-20261013/`, `contention-plans-20261013/`: 보완 전 실제 INSERT 대기와 실행 계획 증거.
- `performance-results/pending-expiration/contention-before-index-hint-20261013/source/`: 보완 전 저장소 쿼리와 진단 코드.
- `performance-results/pending-expiration/contention-index-hint-20261013/`: 보완 후 `samples.json`, `metadata.json`, `controlled-probes.json`, `summary.json` 및 회귀 검증.

- 다른 트랜잭션의 결제 확정을 기다린 뒤 최신 상태 재확인
- 두 실행이 같은 후보를 동시에 처리할 때 중복 만료 방지
- 만료 커밋 보류 중 동일 매물 거절, 다른 매물 생성 성공, 커밋 후 재주문 성공(대상/묶음 1/1, 500/200, 500/500)

스케줄러 단위 테스트는 200건 경계, 빈 후보, 묶음 실패 시 단건 재시도를 확인한다. 기존 단건 만료, 주문 생성, 동시 주문 테스트도 함께 실행한다. 새 회귀 테스트는 일반 `src/test`에 있으므로 `.github/workflows/ci.yml`의 `server-test`가 실행하는 `./gradlew test`에 포함된다. GitHub CI 실행 결과와 로컬 실행 결과는 구분한다.

최초 100건 구현에서 관련 테스트 23개와 서버 전체 테스트 288개가 로컬에서 통과했다. 이후 200건으로 변경하고 2026년 10월 13일 `./gradlew test`를 다시 실행해 전체 288개가 통과했다. 실패·오류·건너뜀은 모두 0건이다. 200건 설정의 로그는 `batch-size-20261013/regression-full.log`, JUnit 결과는 같은 폴더의 `regression-full-xml/`에 보존한다. 이 변경의 GitHub CI는 아직 실행하지 않았다.

이전 500건 설정에서도 `./gradlew test`로 전체 288개가 통과했으며 실패·오류·건너뜀은 0건이다. 당시 설정의 로그와 JUnit 결과는 `batch-size-extended-20261013/regression-full.log`와 `batch-size-extended-20261013/regression-full-xml/`에 있다.

현재 200건과 PK 힌트 보완 후 서버 전체 테스트 **291개가 로컬에서 통과**했다(실패·오류·건너뜀 0). 같은 매물/다른 매물 경합 회귀 3개가 추가됐으며, 결과는 `contention-index-hint-20261013/regression-full.log`, `regression-full-xml/`, `regression-summary.json`에 보존한다. GitHub CI는 아직 실행하지 않았다.

최종 코드의 실제 스케줄러에서도 기존 `PendingExpirationWorkloadTest`를 재실행했다. 50·300·500건의 SQL은 각각 5·9·13회, 트랜잭션은 1·2·3회였고, 미래 만료·결제 확정 주문 보존과 만료·선점 해제 검증이 모두 통과했다. 전체 처리 중앙값은 각각 10.9·35.5·63.9ms였다. 이 별도 실행은 예열·HTTP 구성이 다르므로 위 크기 비교 표와 섞어 비교하지 않는다. 원자료는 `contention-index-hint-20261013/selected-200/`에 있다.

이번 변경에는 테이블·인덱스 변경이 없다. 신규 마이그레이션은 필요하지 않으며, 저장소의 prod 설정은 공통 `application.yml`의 `ddl-auto: validate`를 상속한다. 운영 환경변수로 덮어쓴 실제 값은 별도 확인 대상이다. 기존 수동 SQL 기반 스키마 관리의 마이그레이션 도구 전환은 이번 변경 범위에 포함하지 않는다.

## 재현 명령

`server` 디렉터리에서 Docker와 Java 21이 준비된 상태로 실행한다. MySQL은 테스트 전용 컨테이너를 사용한다. 출력 디렉터리는 실행마다 다르게 지정해서 기존 결과를 보존한다.

./gradlew test

  -Dexpiration.benchmark.batch=true \
  -Dexpiration.benchmark.output=build/reports/pending-expiration-contention \

python3 performance/local-pending-expiration/analyze-batch-size.py \

HTTP 실험은 30초 동안 250회의 목록 조회와 새 주문 생성 흐름을 실행하며, 10초에 만료 메서드를 별도 스레드로 호출한다. 만료 실행·미실행을 각각 3회 비교한다. 요청은 만료 대상과 다른 매물에 생성한다. 부하 발생기와 서버가 같은 JVM을 공유하며 외부 결제는 호출하지 않는다.

최초 100건 구현의 HTTP 요청 3,000건은 모두 성공했고, 각 실행 후 기존 주문 만료와 새 주문 보존을 검증했다. 만료 500건의 처리 시간은 86.0ms, 91.7ms, 87.9ms였으며 SQL은 매번 21회였다. 각 만료 구간과 실행 시간이 겹친 요청은 목록 조회 2건과 새 주문 1건이었다. 이 표본으로 API 지연 감소를 주장하지 않는다. 원자료는 `improvement-20261013/http-after/`에 있다.

개선 후 만료 구간이 짧아지면 그 안에 시작된 HTTP 요청이 없거나 매우 적을 수 있다. 분석 결과의 표본 수 `n`을 함께 보고, 빈 구간의 지연 수치는 `null`로 남긴다. 이 실험은 운영 스케줄러가 다른 정기 작업과 한 스레드를 공유할 때의 지연을 측정하지 않는다. 스케줄러 분리는 별도의 실행 지연 관측을 근거로 결정한다.

## 실제 dev 스케줄러 관측

`dev-scheduler-probe.py before`는 지정된 dev 호스트·프로필·로컬 DB·단건 JAR을 확인한 뒤
전용 합성 회원 2명과 soft delete된 매물 502개를 준비한다. 목록에 노출하지 않고
실제 스케줄러로 이미 기한이 지난 주문 1건 점검 후 500건을 세 번 처리한다.
실제 6분을 기다리지 않으며 만료·검사 설정과 실행 앱을 바꾸지 않는다.
미래 PENDING 1건과 CONFIRMED 1건의 상태·선점을 매번 보존하는지도 확인한다.

100ms 대기와 DB 왕복 사이에 관찰한 최초/최종 커밋 시각의 하한·상한을 기록한다.
전체 스케줄러 실행 시간이나 DB 내부 잠금 시간은 아니다. `completion_after_armed_s`는
