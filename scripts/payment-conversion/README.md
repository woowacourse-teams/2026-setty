# 결제 전환 시나리오와 PostHog 검증

상품 조회, 결제창 이탈, 수동 토스 테스트 결제를 k6 브라우저로 실행한다. 주간 유입을 가정한 100명 시나리오를 압축 실행하여 결제 흐름과 이벤트 수집을 검증한다.

**검증 범위:** 사전에 지정한 행동의 수행 여부, 서버 결제 승인·주문 확정, 실제 앱 이벤트의 PostHog HTTP 2xx 응답이다. 사용자 의도나 복귀 경로가 자발적인 결제 재시도를 늘리는 효과는 검증하지 않는다. 재확인 10명은 같은 상품을 다시 조회하고 종료하며, 결제 재시도는 포함하지 않는다.

## 시나리오와 기대값

구매자 CSV의 처음 100개 고유 계정을 아래 순서로 사용한다. `ACCOUNT_PREFIX=k6usermilan`, `COUNT=100`으로 준비하면 번호는 `001`부터 `100`까지다.

| 그룹 | CSV 계정 순서 | 인원 | 매물 CSV 순서 | 행동 |
| --- | --- | --- | --- | --- |
| A | 1~50 | 50 | 1~20 (조회만, 겹쳐도 됨) | 상품 상세 조회 후 종료 |
| B | 51~80 | 30 | 1~30 (한 명에 한 개) | 상품 조회 → 결제창 열기 → 직접 닫기. 이 중 51~60번 10명은 같은 상품을 한 번 더 조회 후 종료 |
| C | 81~100 | 20 | 31~50 (한 명에 한 개) | 상품 조회 → 결제창 열기 → 사용자가 토스 테스트 인증 수행 → 승인 및 주문 확정 확인 |

결제창을 열면 6분짜리 PENDING 주문이 매물을 잡으므로 B와 C는 매물을 겹쳐 쓰지 않는다. 매물 CSV에 50개 이상이 필요하다. 이전에는 매물 20개를 나눠 써서 `ALREADY_ORDERED` 실패가 날 수 있었으므로, 이전 결과와 비교할 때 결제창 진입·결제 성공 수가 늘었다면 이 배정 변경의 효과다.

판매자·구매자 행정동을 같게 유지한다(#477 이후 결제 금액 일치 조건). 웹은 상세의 고정 배송비로 결제하고 서버는 주문에 저장한 거리 배송비로 검증하므로, 두 동이 다르면 결제가 `PAYMENT_AMOUNT_MISMATCH`로 거절된다. 기본값은 둘 다 `1111053000`이다.

활성 사용자는 관측 주간에 `product_viewed`를 1회 이상 발생시킨 고유 사용자다. 동일 사용자의 재확인 조회는 조회 건수만 증가시킨다.

| 지표 | 선행 `pre_purchase` | 구매 `purchase` | 전체 기대값 |
| --- | --- | --- | --- |
| 상품 조회 고유 사용자 / 가상 WAU | 80 | 20 | 100 |
| 상품 조회 이벤트 | 90 | 20 | 110 |
| 결제창 진입 | 30 | 20 | 50 |
| 결제창 닫기 | 30 | 0 | 30 |
| 재확인 사용자 | 10 | 0 | 10 |
| 결제 완료 | 0 | 20 | 20 |
| HTTP 2xx를 확인한 PostHog 이벤트 | 230 | 80 | 310 |

확인 이벤트 수에는 로그인 `$identify`가 포함된다. 선행은 식별 80 + 조회 90 + 열기 30 + 닫기 30, 구매는 식별 20 + 조회 20 + 열기 20 + 결제 완료 20이다. 자동 페이지 조회·Web vitals 등은 이 수에 포함하지 않는다.

- 최종 결제 전환율: 결제 완료 고유 사용자 20 / 상품 조회 고유 사용자 100 = 20%.
- 결제창 진입 대비 전환율: 결제 완료 고유 사용자 20 / 결제창 진입 고유 사용자 50 = 40%.

**이 비율은 시나리오 기대값이다.** 실사용자의 전환율이나 목표 수치의 타당성을 보여주는 데이터로 해석하지 않는다. k6 카운터의 고유 사용자 의미는 서로 다른 계정을 한 번씩 사용하는 이 실행 조건에 의존한다. PostHog에서는 고유 사용자 기준으로 별도 대조한다.

모든 명령은 저장소 루트에서 실행한다. Bash 4.2 이상, 브라우저를 지원하는 k6, Chrome/Chromium, `curl`, `python3`이 필요하다. 로컬 회귀 테스트에는 Node.js도 필요하다. 이번 작업에서 k6 2.3.0, Node.js 22로 검증했다.

- 실제 시나리오: 공유 프론트엔드 `https://www.setty.cloud`, API `https://www.setty.cloud/dev`. 토스 테스트 인증은 직접 완료한다.
- 계정·매물 CSV: `.local/`에 보관한다. 구매자 CSV에는 평문 비밀번호가 있어 Git에서 제외한다.
- 선행 단계: A/B 최대 4 VU. 성공한 뒤 C 최대 2 VU를 실행한다. 선행 예외 또는 임계값 실패는 구매 단계를 중단한다.
- 실패 로그: `.local/k6-run.*`에 보존한다. 성공 실행의 임시 로그는 삭제하므로 보고서용 요약은 따로 보관한다.
- 로컬 회귀: 실제 dev·토스·PostHog에 요청하지 않고 loopback 서버와 합성 토큰을 사용한다. 결제 복귀 7개와 모달 닫기 5개 사례다.

서버 승인 키 기본값은 [application.yml](../../server/src/main/resources/application.yml), 공개 테스트 클라이언트 키는 [tossPayment.ts](../../client/src/payment/tossPayment.ts)를 참조한다. 키 값을 이 문서에 중복 기록하지 않는다. `TOSS_SECRET_KEY` 환경변수는 서버 기본값보다 우선한다.

## PostHog 필터와 관측 결과

프로젝트 `640788`의 [밀란 주간 상품 조회·결제 전환 대시보드](https://us.posthog.com/project/640788/dashboard/2196165)를 사용했다. 모든 카드에 같은 기간과 테스트 계정 코호트를 적용한다.

- WAU: `product_viewed`의 주간 고유 사용자.
- 상품 조회→결제: `product_viewed → payment_succeeded`, 고유 사용자 퍼널.
- 결제창→결제: `checkout_opened → payment_succeeded`, 고유 사용자 퍼널.

한 주 동안의 자연 유입을 관찰한 자료가 아니라 주간 유입을 가정한 시나리오다. 이벤트가 발생한 실행 일시를 포함하는 기간으로 조회하고 시간대도 기록한다. 여러 실행이 같은 기간에 포함되면 해당 기간의 합산 고유 사용자 지표가 된다.

코호트 가져오기용 CSV는 비밀번호와 헤더를 제외한 로그인 ID만 넣는다.

```sh
awk -F, 'NR > 1 { print $1 }' .local/k6-test-users-milan.csv \
  > .local/k6-milan-loginids.csv
```

ID가 해당 PostHog 프로젝트에 식별된 뒤 가져온다. 전부 매칭되지 않으면 먼저 프로젝트와 `distinct_id`를 확인한다. 자세한 가져오기 규칙은 [PostHog 코호트 문서](https://posthog.com/docs/data/cohorts)를 참조한다. 이벤트가 없으면 코호트 필터를 잠시 제외해 같은 기간의 이벤트 존재 여부를 확인한 다음 다시 적용한다.

HTTP 2xx는 수집 서버의 접수 확인이다. 대시보드 집계 반영은 별도로 확인한다. `응답 대기`는 전송 요청을 관측했지만 아직 응답을 확인하지 못한 상태다. 앞선 화면 동작이 실패하면 후속 수집 검증도 실행되지 않을 수 있으므로 확인 이벤트 수 감소만으로 PostHog 장애를 단정하지 않는다.

2026-10-11 확인한 대시보드 관측값은 다음과 같다. 단건 스모크가 포함되어 시나리오 기대값과 차이가 난다.

| 구분 | 상품 조회자 | 결제창 진입자 | 결제 완료자 | 조회→결제 | 진입→결제 |
| --- | --- | --- | --- | --- | --- |
| 시나리오 기대값 | 100 | 50 | 20 | 20% | 40% |
| 관측값 — 스모크 포함 | 100 | 51 | 21 | 21% | 41.18% |

스모크 구매자도 같은 100명 코호트에 속하므로 조회 고유 사용자 분모는 100명이다. 여러 실행이 섞인 대시보드 결과만으로 단일 전체 실행의 모든 k6 임계값이 통과했다고 판단하지 않는다. 스모크 제외 결과가 필요하면 실제 실행 기간으로 분리하여 다시 조회한다.

이번에 재확인 10명에게 구매를 추가하지 않은 이유는 기본 이벤트·전환 지표의 검증 범위를 유지하기 위해서다. 사전에 재구매를 지시하면 연결 경로의 기능 검증은 추가할 수 있지만, 상세 복귀가 자발적 재시도를 높였다는 근거는 생기지 않는다. 현재 가설의 효과는 판단 보류이며, 재확인 후 결제 재시도 흐름은 별도 미검증 항목으로 남긴다.
